## 3. Goose・Rust・Go・Zig・C++の機能比較

評価記号よりも**機能の性質**を重視して整理する。

| 項目 | Goose | Rust | Go | Zig | C++ |
|---|---|---|---|---|---|
| Generics | あり、特殊化中心 | Generics / Trait | 型パラメータ / Interface | `comptime`を軸に構成 | Template / Concept |
| 代数的データ型 | ADT | `enum` | 直接のADTは限定的 | Tagged Union | `std::variant`等 |
| 動的ディスパッチ | 制約が強い | Trait Object等 | Interface | 明示的な関数テーブル等 | Virtual Function等 |
| 借用・寿命の静的検証 | Rootとスコープによる解析 | 所有権・Borrow Checker | なし（Escape Analysisは配置最適化） | 開発者の責任 | RAIIと開発者の責任 |
| 一般的なヒープ使用 | 通常値ではなし | 使用可能 | GC管理ヒープ | 明示的Allocator | 使用可能 |
| 汎用の関数値 | 静的関数値が中心 | 対応 | 対応 | 対応 | 対応 |
| エラー処理 | 複数戻り値、`return ... from` | `Result`、`?` | `error`戻り値 | Error Union、`try` | Exception、`expected`等 |
| 並行処理 | 分離Worker・型付きキュー | Thread、async、Channel | Goroutine、Channel | Thread・ライブラリ | Thread、Coroutine等 |
| 共有メモリの制御 | 意図的に制限 | `Send`/`Sync`、Lock、Atomic | Lock、Atomic、Channel | Lock、Atomic等 | Lock、Atomic等 |
| Cとの相互運用 | `extern` / `export`等 | FFI | cgo等 | C ABIとC連携に強い | 非常に強い |
| `no_std` / ベアメタル | 現行モデルは不向き | 対応 | 標準処理系は不向き | Freestanding対応 | 環境依存で対応 |

### 関数値・抽象化・コンパイル時計算の違い

RustやGoでは、関数やクロージャを実行時の値として保持・受け渡せる。Gooseの**Static Function Value**は基本的にコンパイル時の引数であり、非脱出の高階関数を専用化して呼び出す。したがって、ループ内のコールバックを直接呼び出しへ変換しやすい一方、実行時に未知のプラグイン関数を取り替える構造には向かない。[1](references.md#ref-1)

Zigの`comptime`とC++のTemplateもコンパイル時計算・特殊化に強いが、Zig/C++には通常の関数ポインタやランタイム上の柔軟なディスパッチ手段がある。RustのTraitは静的ディスパッチと動的ディスパッチを使い分けられる。

### エラー処理とコード生成

Gooseの`return ... from`は外側の関数への長距離復帰を可能にするが、例外と同一ではない。Rustは`Result`と`?`、Goは`error`戻り値、ZigはError Unionと`try`、C++は例外や`std::expected`を利用する。ここでの差は記述量だけでなく、**呼び出し元へのエラー契約とリソース解放責任**にある。

Gooseの`simd fn`は命令セット別の実装を生成・選択する仕組みで、`checkfree fn`は境界検査の消去をコンパイル時に検査する宣言である。ただし、現行Cバックエンドでは`simd fn`の効果は対象CPU・コンパイラに依存し、たとえばJITや一部バックエンドでは無視される。また、境界検査が消えてもベクトル化は保証されない。公式`blur`ベンチマークは、Cコンパイラによる生成コードの差を示している。[1](references.md#ref-1)[3](references.md#ref-3)

### Gooseの安全性はRustと同じではない

RustのBorrow Checkerは、特にエイリアスと変更可能性の規則を通じて、幅広いデータ構造を安全に管理する。一方Gooseは、値を置ける場所と寿命の重なりを制約することで、解放済みメモリへの参照などを防止する。[1](references.md#ref-1)

Rustでは排他的な可変借用が必要な操作も、Gooseでは「伸長しても元の要素が移動しない」ため可能になる場合がある。これは有効な設計上の利点であって、Gooseの方がすべての安全性でRustより強いという意味ではない。

### Gooseの並行処理はGoのGoroutineと異なる

GooseのWorkerは独立したメモリ領域を持つOSスレッドを使い、型付きキューを通じてFlat Valueをコピーする方式を基本とする。**GoのGoroutineのような大量の軽量タスクを直接置き換える仕組みではない。**共有可変メモリの競合を避けやすい反面、巨大な共有データをゼロコピーで共同処理する用途や、大量の軽量なI/Oタスクには制約がある。2026年の処理系には`thread_spawn_contained`や、型付きキューの容量制限・時間制限付き受信もある。ただし、**`thread_spawn_contained`が局所化するのは言語ランタイムの特定の`abort`であり、ガードページ違反、ネイティブスタック枯渇、`exit`、ランタイム自身の故障まで隔離するわけではない**。`extern fn`が開いた外部資源も自動的には閉じられない。内部キューはMutexとノード割当を使用しており、「あらゆる同期・割当がゼロ」でもない。[1](references.md#ref-1)[2](references.md#ref-2)[14](references.md#ref-14)

GoのGoroutineは大量のI/O並行処理に向き、GoのGCは管理の容易さを提供する。Escape Analysisは配置の最適化であり、RustのBorrow Checkerのように別名参照の安全性を証明する機構ではない。共有メモリを使えば競合が起き得るし、ヒープ割当を減らす調査も必要になる。[6](references.md#ref-6)[7](references.md#ref-7)

## 4. 制約を先に理解する：Gooseが諦めた自由度

### 4.1 再帰や動的な寿命に制約がある

再帰呼び出しをまたいで伸長可能なローカル値を保持することには制限がある。必要な領域を再帰の外で確保し、参照として渡すなどの設計変更が求められる。

これは性能のための制約だが、どのアルゴリズムも自然に記述できるわけではない。例えば、リクエスト単位の一時データは寿命を揃えやすい一方、LRUキャッシュのエントリは個別に失効する。後者では`slot_pool<T>`・`slice_pool<T>`、インデックスや世代付きハンドルなどを設計する必要がある。[1](references.md#ref-1)[13](references.md#ref-13) **実行速度だけでなく、構造の変更しやすさも評価対象**となる。

<a id="memory-exhaustion"></a>

### 4.2 リアルなメモリ不足は消えない

仮想アドレス空間を予約しても、物理メモリは有限であり、OSやコンテナのメモリ制限も存在する。Gooseでは予約領域の末端やOS側のコミット不能などに対するランタイム処理があるが、任意の動的確保を失敗可能な`Result`として継続処理できる汎用Allocatorモデルとは異なる。Linux/macOSのように予約した範囲をマップするOSでは、物理メモリ割当の失敗が発生するタイミングもWindowsとは異なる。[2](references.md#ref-2)

これは**可用性と入力検証**の問題でもある。信頼できない外部入力に応じて大きなData Stackを伸長する処理では、サービス全体の異常終了やOS側のOOMに至る可能性を考慮すべきである。入力サイズの上限、処理単位の隔離、メモリ予算、異常時の復旧方針を設計する必要がある。さらに、**スタック本数に基づくコンパイル時制約と、OSが実際にメモリを供給できるかという実行時制約は別**である。速い解放と、限られたメモリで安全に継続稼働できることは別である。

Zigのようにアロケータを明示的に受け取る設計は、このような環境制約をライブラリAPIに反映しやすい。[10](references.md#ref-10)

### 4.3 GCがなくても、リソース解放問題は残る

Data Stackの巻き戻しは**メモリ領域の再利用**を意味するが、開いたファイル、ソケット、GPUリソース、暗号鍵の消去、外部ライブラリが確保した領域まで自動的に処理するとは限らない。Gooseにも`defer`やFFIはあるが、Rustの`Drop` / RAII、Zigの`defer` / `errdefer`、C++のデストラクタとは、設計上の責任分担が異なる。リソースの所有関係をAPIとして明文化する必要がある。[1](references.md#ref-1)[2](references.md#ref-2)

### 4.4 安全性は論理的正しさの代わりにならない

型安全な参照であっても、Poolのスロットが再利用された場合に「今は別のオブジェクトが入っている」という論理的な不整合は起こり得る。Goose仕様はこうした*Type-safe stale references*をメモリ安全性とは別の問題として扱っている。[1](references.md#ref-1)

これらの制約を言語の欠陥と断ずる必要はない。むしろ、**何を諦めると、何をコンパイラに保証・最適化させられるか**を明確にする設計である。

### 4.5 メモリ配置が良くても、生成コードが不利になる場合

Gooseの弱点は「Poolが必要なケース」に限らない。公式ベンチマークの設計文書は、次の性能リスクを**意図的に検証対象として列挙**している。[11](references.md#ref-11)

| 性能上の論点 | Gooseの強みとの関係 | 実装時の注意 |
|---|---|---|
| **Alias（別名参照）** | Gooseは同じ領域への複数参照を柔軟に許容する | Rustの排他的`&mut`やC/C++の`restrict`に相当する最適化ヒントをバックエンドへ常に渡せるわけではない。ループのベクトル化が妨げられ得る |
| **大きな値のコピー** | 新しい可変長値を最終配置先へ直接構築でき、可変長の既存値の暗黙コピーは禁止される | 大きい**固定サイズ値**には暗黙コピーがあり得る。可変長値でも独立した複製には`copy`が必要。Rustの`Vec`などのO(1)所有権ムーブとは異なる |
| **密なパック配置** | 容量・参照・パディングを削ってCache利用を改善できる | 自然なアラインメントが必要なSIMD処理では、非アラインアクセスやコード生成上の不利が生じ得る |
| **相対参照の復号** | ポインタを小さくし保存・走査時のデータ量を減らせる | オフセット計算やリンク更新の負担があり、更新頻度の高い構造では整数Index方式が有利なことがある |

例えば、公式`blur`ベンチマーク（8192×8192の画像へ3×3フィルタを16回適用）では、**Gooseの両実装とも境界検査の除去が検証済み**にもかかわらず、次の差がある。[3](references.md#ref-3)

| 実装 | MSVC | Clang |
|---|---:|---:|
| Goose：フラットなインデックス参照 | 952.1 ms | 266.0 ms |
| Goose：行スライスを使用 | 297.9 ms | 269.2 ms |
| Rust：フラットなインデックス参照 | 299.2 ms（rustc） | — |

同じ画像処理でも、参照の形によって生成される機械語が変わり、MSVCでは約3.2倍の差が生じた。公式実装ノートではエイリアス解析やベクトル化の問題が説明されているが、**この表の数値だけから個々の原因の寄与率までは特定できない**。**境界チェックを消せたこと、アロケーションが安いこと、最適な機械語が生成されることはそれぞれ別の問題**である。Goose公式の結果も、この三者を切り分けて解釈する必要がある。

これはGooseの有効性を否定するものではなく、**メモリ配置が効率的でも、生成機械語とアルゴリズムの最適化は残る**という例である。測定時にはメモリ律速・計算律速・分岐律速・I/O律速を分けて診断したい。

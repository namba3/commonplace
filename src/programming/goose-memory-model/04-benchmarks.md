## 6. ベンチマークから読み取れること、読み取れないこと

Goose公式の比較資料には、通常の所有ノードとArenaベースの実装を分けたケースが含まれる。**ただし全ベンチマークが同じデータ表現・所有条件で比較されているわけではない。** 言語仕様の効果、データ構造、コンパイラの生成コード、入力構築方法を分離して読み解く必要がある。[3](references.md#ref-3)[11](references.md#ref-11)

**測定条件（重要）：** 公開表は2026年10月16日に生成され、Windows 11 / AMD Ryzen 9 9950X3D / 94GB RAMの**単一マシン**で計測された。コンパイラ本体は当時の`f6d31d0e`を基にビルドされ、ベンチマークのソースには同日の更新が加えられている。記事の調査日時点のGoose仕様と、性能測定時点のコードを同一視してはいけない。GooseとC++はMSVC（`v145`）またはClangでビルドし、Rustは`rustc`による1種類のビルドを掲載。各値はウォームアップ2回後の3回から最速値を採用し、CPUコア固定は行わず、入力生成・処理・破棄を含むプロセス全体の経過時間である。メモリ列は大規模ケースのPeak Working Set（Goose/C++では二つのCコンパイラの測定値をまとめた列）であり、仮想アドレス予約量ではない。[3](references.md#ref-3)

公式資料自身が、**同一マシンのこの測定系では約10%未満の差は測定ノイズの範囲に入る**と注意している。なお、結果ページ後半の「Historical analysis through October 10」は過去の実験記録であり、その結果・因果説明のすべてが10月16日に再測定されたわけではない。とくに`graph`のLinked形式と`lru`では目安が約15%である。これはすべてのベンチマークに適用できる普遍的な誤差率ではなく、**この測定条件について開発元が示した注意**である。したがって、数%の差から一般的な性能順位を導くことは避ける。[3](references.md#ref-3)

### 6.1 木構造を構築して走査する例

公式`tree`ベンチマークの大規模ケース（深さ24）では、次の値が示されている。[3](references.md#ref-3) **Goose側は「何も調整していない素朴なツリー」ではなく、Poolと型付き相対参照を使った専用実装**である。

| 実装 | 大規模ケース時間 | Peak Working Set |
|---|---:|---:|
| Goose：Pool + 型付き相対参照（MSVC） | 618.0 ms | 391.8 MB（共通集計値） |
| Goose：同（Clang） | 658.3 ms | 391.8 MB（共通集計値） |
| Rust：`Box`でノード所有 | 2,777.8 ms | 1,038.7 MB |
| Rust：Arena + Index | 675.8 ms | 391.5 MB |
| C++：Arena + Index（MSVC） | 733.9 ms | 391.5 MB |
| C++：Arena + Index（Clang） | 737.3 ms | 391.5 MB |

注：Gooseの391.8 MBは公式表でMSVC/Clangを横断して集計されたPeak Working Setであり、両バックエンド個別の測定値ではない。

この条件では、Rustの`Box`ノード表現と比べ、GooseのPool構造は大幅に効率的である。しかしRustのArena + Index版では差が小さくなる。**比較されているのは「GooseのPool実装」と「Rustの二種類の所有・配置モデル」であり、言語だけを取り替えた条件ではない。**

**この測定は各実装の配置方式を含む総合結果であり、言語単体の寄与は特定できない。** とくにClangのGooseとRustのArena版の差は約2.6%（658.3ms対675.8ms）であり、公式資料のノイズ上の注意から、優位性を確定できない。GooseのMSVC版との比較でも約9%である。RustはLLVMによる一つのビルドで、公式資料は比較先としてClang系の列をより近い条件としている。ただし、同じ最適化フラグやバックエンドそのものを使った比較ではない。加えて、`Box`版とArena版はデータの所有関係と参照インターフェースにも差がある。

### 6.2 得意・不得意の差を見せる対照ケース

| 処理 | Goose（MSVC / Clang） | 対照実装 | 読み取れること |
|---|---:|---:|---|
| `push`：64M件を追加して参照を保持 | 162.1 / 162.0 ms | Rust `Vec::reserve` + Index：174.3 ms | Gooseは型付き参照、RustはIndexを保持。アクセス契約が異なるうえ、差は公式のノイズ目安より小さい |
| `calc`：1.6M件の式を解析・評価 | 481.4 / 490.8 ms | Rust Arena + Result：435.8 ms | 公式の測定ではGooseが劣る |
| `particles`：浮動小数点の粒子更新 | 実装によって差がある | Rustの配列処理 | AoS/SoAやループ形状・バックエンドを揃えて比較する必要がある |
| `graph`：2M頂点・隣接構造の構築とBFS | Linked：3,911.7 / 4,078.0 ms、CSR：698.5 / 616.5 ms | 同じGoose言語内の2方式 | データ表現・構築手順によって5倍以上の差が生じる |

`push`ではGooseが要素への型付き参照を保持する一方、Rustはインデックスを保持する。**両者が提供する参照APIの性質は同一ではない**ため、「同一プログラムの言語差」とは言えない。`calc`にはエラー伝播・数値表現・グローバルカーソルなど複数の実装差があり、単一の言語機能を原因と断定できない。一方、`particles`はAoS/SoAやループ形状・バックエンドの選び方で差が変わるため、数値計算における一律の優劣を示さない。`graph`では**同じGoose同士でも、1パスのLinked形式と2パスのCSR（Compressed Sparse Row）で5倍以上の差**がある。これはデータ配置に加え構築手順・アクセス局所性も違うため、**データ表現「だけ」の純粋な効果と見なしてはいけない**。**計算全体がアロケーションに律速されないなら、別の最適化が支配的になる。**[3](references.md#ref-3)

### 6.3 旧APIを使ったベンチマークが残っている

Gooseの公式`lru`ベンチマークは、2026年10月16日の公開表でも**非推奨の`reusable` Pool**を使っている。一方、現在推奨されるのは`slot_pool<T>`などのライブラリ実装であり、両者の移行には互換性・性能上の確認事項が残っている。[3](references.md#ref-3)[13](references.md#ref-13)

したがって、`lru`の**2,759.9 / 2,067.9 ms**という数字を、最新の`slot_pool<T>`を使ったアプリケーションでも当然得られる性能として引用してはいけない。また、RustのArenaとの比較も、参照形態、失効ルール、テーブル方針などを揃える必要がある。この点は「Gooseでも配置・Pool設計が不要ではない」という本稿の主張を裏付けている。

### 6.4 公式の幾何平均は何を示すか

16ベンチマークの大規模ケースで、Gooseの速度倍率は次のように報告されている（**1超ならGooseが速い**）。

| 比較先 | MSVC版のGoose | Clang版のGoose |
|---|---:|---:|
| 通常のC++実装 | 3.51倍 | 3.54倍 |
| 手動最適化したC++実装 | 1.24倍 | 1.26倍 |
| 各ケースで速いSafe Rust実装 | 1.13倍 | 1.19倍 |

これは対象ワークロードにおける**プロジェクト独自ベンチマークの幾何平均**であり、他のPC、OS、コンパイラ、アプリケーションで再現される一般的な性能比を意味しない。**同じ問題を異なるデータ表現で実装しているケースも含まれるため、言語仕様・アルゴリズム・データ構造・最適化品質の効果は分離されていない。**特に集計表は、各ベンチマークで**速度について最速の実装を選択し、メモリについては別に最小メモリ実装を選択**している。例えば`graph`では、最速時間は**2パスCSR版**（Clangで616.5 ms）から、最小メモリは**Linked版**（160.5 MB）から採られている。CSR版の実際のメモリは221.7 MBであり、「616.5 msかつ160.5 MB」という単一の実装が存在するわけではない。このような組み合わせを性能とメモリの両立実績として引用してはいけない。[3](references.md#ref-3)

Rust版にも`Box`型とArena型が含まれ、各行で同じデータ表現を採っているとは限らない。なお、**GoとZigの結果はこの公式比較の対象外**であり、同じ表からこれらの言語との速度差を論じることはできない。[3](references.md#ref-3)[11](references.md#ref-11)

### 6.5 望ましい比較の方法

記事の中心仮説が「初期実装から効率的な配置が得られ、最適化工数が減る」である以上、**最速実装同士の数値だけでは仮説を直接検証できない**。Goose側にもPool・相対参照・CSRの選択が必要なら、その実装時間を含める必要がある。性能と実装負担を両方評価するには、少なくとも次の条件を揃えたい。

1. 同じアルゴリズム、入力、出力、検証条件。構築・破棄を含む全体時間と、処理カーネル単独時間を分ける。
2. 通常実装と、言語固有の最適化実装を分ける。
3. Rust/C++/ZigでもArena、Pool、相対参照を使った対照群を設ける。Goも比較に入れるならGCの通常実装とアロケーション削減版の両方を測る。**Gooseの公式16件にはGoとZigの結果がないため、別途同じ課題を実装して測定する。**
4. スループットだけでなく、p95/p99レイテンシ、最大RSS、予約仮想メモリ、確保回数、Cache Missを測る。OSのPage Fault・Commit量も区別する。
5. コード量、実装労力、ビルド時間、保守性も合わせて評価する。言語ごとに同等の設計・習熟時間を与え、**初期実装・最適化後・機能変更後**を別々に計測する。
6. 大規模入力、メモリ不足、長時間稼働、複数スレッドの条件を試す。CPU固定、ウォームアップ、測定分布も揃える。バイナリ、コンパイラの版、フラグ、ソースのコミットを固定する。**大きな値の移動・参照の別名・SIMD/非整列アクセス**を個別に変化させる対照実験も用意する。

重要なのは、**初期実装での効率と、専門家が最適化した後の到達性能を別に測ること**である。Gooseに期待されるのは、絶対速度だけでなく性能目標に届くまでの最適化作業を減らすことだからだ。公式の`graph`では表現と構築手順を変えた際の差が、言語間の小さな差を上回る。[3](references.md#ref-3)[11](references.md#ref-11)

### 6.6 読者が追試するための最小手順

各サンプルは`fn main()`を含むため、**別々の`.goose`ファイル**として試す。まず、[公式Releases](https://github.com/aardappel/goose/releases)から対象OS用の処理系を用意し、[第1部・第2.2節の伸長配列の例](01-memory-model.md#nonmoving-array-example)を`sample.goose`として保存する。次のCLIは公式コマンドリファレンスに記載されている。[19](references.md#ref-19)

```bash
goose version                         # コンパイラ／ランタイムの版を記録
goose toolchain                       # 認識されたCコンパイラ等を確認
goose check sample.goose             # 構文・型・寿命の静的検査
goose check sample.goose --stacks    # Data Stack本数の確認
goose run sample.goose               # TinyCCでインプロセス実行
goose build sample.goose             # ネイティブ実行ファイルを生成
```

**動作確認時の期待出力：** [第1部・第2.2節](01-memory-model.md#nonmoving-array-example)の最初の`i64[>..]`の例を保存したなら、`check`が成功し、`run`で`100000`が出力されることを確認する。続いて`build`で生成された実行ファイルでも同じ結果になることを確認する。[同節](01-memory-model.md#nonmoving-array-example)の`Entry`参照の例を別ファイルにした場合の期待値は`11`である。

`--bce-lines`は**配列アクセスを含むコードの境界検査**を分析するオプションである。上の`sample.goose`は配列の添字アクセスを行わないため、そこで境界検査除去の効果を確認するのは適切でない。添字アクセスを含む別のテストについて`goose check <ファイル> --bce-lines`を実行し、削除・残存数を確認する。ただし境界検査の除去は、SIMD化やループ全体の高速化まで保証しない。

`goose run`は手軽な動作確認向けで、**最適化性能の測定には`goose build`で作成した実行ファイル**を使う。公式の`-O0`〜`-O2`はGoose側のインライン化程度を主に調整するもので、生成Cコードに使うCコンパイラの最適化設定とは区別する。スレッドを作成するGooseプログラムは、現行のTinyCC実行モードでは動かせない。Linuxで`run`する場合はCライブラリのヘッダー、`build`には対応するCコンパイラ等が必要になる。`check`の成功、実行結果の一致、性能測定はそれぞれ別の検証である。[19](references.md#ref-19)

配布版v2026.3と更新中の仕様・例には版差があり得る。コマンドの挙動を比較する際は版とソースのコミットを揃える。この手順で扱うのは静的検査と小規模な実行例であり、**公式16ベンチマークの性能比較とは別である**。性能を比較する場合は対象コード、Cコンパイラ、入力、測定環境、ウォームアップ条件を揃える。

## 要旨

**Gooseの魅力は、Rustより常に速いことではない。効率的なメモリ配置を、専用アロケータの明示的な導入に頼らず、言語の通常の機構として使える点にある。** 複数のData Stack、非移動の伸長配列、スコープ単位の解放、可変長データのインライン格納などを組み合わせる。RustやC++でも既存のArenaライブラリを利用でき、毎回アロケータを自作する必要はない。ただし、その選定・適用範囲・寿命を開発者が設計する点が異なる。

ただし、GooseにもPoolの選択、データ構造、寿命の設計が残る。仮想アドレス予約に依存する現在のランタイムは、Kernel・UEFI・ベアメタル向けではない。**製品全体の採用ではRust・Go・Zig・C++の成熟度が優位で、Gooseはデータ配置の研究と、短命データを扱う独立した処理のPoCで注目に値する**、というのが本稿の結論である。

本稿でいう「自動化」とは、最適なアルゴリズムを自動選択することではなく、**効率的なメモリ確保・配置・寿命管理を、言語の標準的な型と実行モデルが支えること**を指す。その効果は次の三つの観点で評価する。

1. **実装コスト**：効率的なメモリ配置を得るため、開発者は何を実装・設計する必要があるか。
2. **実行性能**：同じ問題に対して、どのデータ構造・処理系がどの程度高速か。
3. **採用可能性**：必要なOS、ライブラリ、保守体制まで含めて選べるか。

### 先に結論を整理する

| 問い | 現時点の答え |
|---|---|
| Gooseならアロケータの手動最適化が不要か | **一部では不要**。Data Stackの管理・一括解放・非移動伸長などを標準的なモデルとして利用できる。ただしPool、データ表現、寿命の設計は残る。 |
| Gooseは最適化済みRustより常に速いか | **いいえ**。同じArena型の表現と比較すると差が縮まる例があり、Gooseが負けるケースもある。言語差とデータ表現差は分離して考える。 |
| なぜ任意の用途に使えないのか | データの寿命・所有関係と、仮想メモリを前提とするランタイムに制約がある。 |
| いま新規プロジェクトに採用すべきか | 研究・PoC・独立した短命データ処理では検討余地がある。製品全体ではRust・Go等の成熟度を優先するのが堅実。 |
| Gooseの発想はRustなどに影響するか | **十分あり得るが、現時点で直接の影響関係を示す証拠はない**。まず既存crateやライブラリ設計への波及が考えられ、標準ライブラリ・言語仕様への採用は別段階の議論。 |
| Gooseの標準ライブラリは成熟し得るか | **可能性はあるが未確定**。モジュール数だけでなく、API安定性、主要用途の実装事例、テスト・保守体制、実行環境への移植性が鍵になる。 |

## はじめに：性能最適化を「書く側」の責任から減らせるか

RustやC++ではまず標準コンテナを使い、割当・局所性がボトルネックになった段階でArena、Pool、事前容量予約、コンパクトな表現へ切り替えることが多い。ZigではAllocatorを明示的に選びやすく、GoはGCとEscape Analysisによって日常的なメモリ管理を軽くするが、性能要求が厳しければ調整が残る。

Wouter van Oortmerssen（aardappel）の実験言語**Goose**は、この設計判断の一部を言語の通常モデルへ移す。汎用ヒープに頼る代わりに、コンパイラが複数の*Data Stack*を割り当て、非移動の伸長配列、スコープ一括解放、インライン可変長データ、相対参照を提供する。[1](references.md#ref-1)[2](references.md#ref-2)[12](references.md#ref-12)

本稿では、**初期実装の手間・最適化後の到達性能・製品としての実用性**を分けて評価する。

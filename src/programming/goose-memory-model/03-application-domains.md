## 5. 用途別適性：どこで何を選ぶべきか

以下は**2026年10月時点の実用開発における筆者の定性的判断**である。理論上の実装可能性だけでなく、言語の成熟度、周辺ライブラリ、OS・CPUターゲット対応、既存の開発資産を考慮した。◎は有力な第一候補、○は実用的な選択肢、△は対応に条件や大きな制約がある、×は現行実装では一般的に不向きを意味する。**記号は実行速度・メモリ安全性のランキングではない。** とくに低レベル分野では、評価はターゲットの種類によって変化する。

Rustの`no_std`やZigのFreestandingは低レベル実装の重要な土台だが、**Kernel/Driver/Hypervisorの◎を自動的に意味しない**。Linuxの既存API、対象アーキテクチャ、デバイス・ブート規格、リンカ・割り込み・メモリ初期化などの適合確認が必要になる。C++も利用例はあるが、特にLinux Kernelの主流言語として扱うのは不適切である。

ここでのGooseの`△`は**現時点の製品開発・保守という観点**である。短命データ処理の**言語設計上の潜在力**は高くても、ライブラリ・利用事例・ツールの成熟度とは別である。*PoCや研究対象としてなら、パーサー・レコード処理は特に有望である*。この表の記号をマイクロベンチマークの速度順位に読み替えてはいけない。

### 5.1 Webフロントエンド

ブラウザ向けUIでは、比較表にはないTypeScript/JavaScriptが事実上の実用基準になる。表の各言語の○や△は、TypeScriptへの優位を示すものではない。RustはWebAssemblyやDioxus、Leptos、Yewなどによる選択肢を持つが、ブラウザ資産との連携や周辺ライブラリではTypeScriptが有利な場面も多い。

GoはサーバーサイドHTML生成には適しているが、通常のGo処理系によるブラウザWasm実装は一般的なUIの第一候補ではない。

Gooseについては、**WebAssembly対応は設計提案であり、現行の実装済み機能ではない**。Wasmを出力できるCコンパイラがあるというだけでは、Gooseのランタイムまで対応することにはならない。現在のData Stackは仮想アドレス予約と安定アドレスに依存するため、Wasm Linear Memoryに移植する際は参照形式や伸長方法の再設計が必要になる。[4](references.md#ref-4)

### 5.2 Webバックエンド・分散システム

GoとRustが有力である。Gooseはリクエスト内の一時データに向く可能性があるが、接続・セッション・キャッシュには別の寿命管理が要る。

- **Go**：HTTP、DB、Goroutine、標準ツールなどが統合され、単純さとチーム開発効率に強みがある。
- **Rust**：Tokio、Axumなどのエコシステムを使え、ネットワーク処理と高度なデータ処理を同じ言語で実装しやすい。
- **Goose**：リクエストごとにデータを作り一括破棄する計算部分には可能性があるが、非同期I/Oや接続管理、キャッシュ、認証、ミドルウェアなどの成熟した基盤は不足する。

I/O待ちやDB応答が律速なら、アロケーションの改善は全体性能に直結しない。

### 5.3 OS Kernel・Driver・Hypervisor

この領域では、任意アドレスへのアクセス、MMIO、DMA、割り込み、ページテーブル、Atomic、特権命令、特殊なアロケータなどが必要になる。

Rustは`#![no_std]`、Raw Pointer、`unsafe`、Inline Assemblyなどを通じてOSに依存しない低レベルコードを書ける。Linux KernelにもRust用の開発・ビルド支援が存在する。ただし、各サブシステムのRust APIや既存資産の成熟度は一様ではなく、**カーネルを作れるという言語上の能力と、既存のLinuxドライバ開発で何を実装できるかは別**である。[8](references.md#ref-8)[9](references.md#ref-9)

ZigはFreestandingや明示的なAllocatorを利用でき、低レベル制御に向いている。ただし、Rustと同水準の静的メモリ安全性を自動的に得られるわけではない。[10](references.md#ref-10)

Gooseの現行ランタイムはData Stack用の仮想アドレス予約、OSのページ処理、専用の初期化を前提とする。デフォルトの予約サイズはData Stack当たり2 GiBで、確保可能な領域が小さい場合には縮小を試みる。**2 GiBの物理RAMを最初から消費するという意味ではない**が、仮想メモリ管理のない環境でそのまま動かせるわけでもない。[2](references.md#ref-2)

このため、**現在公開されているGoose処理系を前提にする限り**、KernelやHypervisorを直接実装する主言語としては適していない。**「GCがない」「Cを生成する」は、`no_std`やFreestanding対応、MMIO・DMA・割り込み・Atomicを実装できることと同義ではない**。Gooseに必要な機能を後付けするなら、ランタイムだけでなく安全性の前提も再検証しなければならない。

### 5.4 BIOS・UEFI・Bootloader

従来型BIOSの16bit初期起動と、UEFIのアプリケーション・ドライバは分けて考える必要がある。

UEFIには実行形式、ABI、Boot Services、Runtime Servicesなどの規定があり、Cに加えてRustやZigによる開発も可能である。**UEFIアプリケーションを生成できることと、任意のUEFIドライバやOS起動段階の処理を十分に実装できることは別**である。RustにはUEFIターゲットや`uefi` crateがある。TinyGoにもUEFIアプリケーション向けのドキュメントがあり、**「GoはUEFIで一切使えない」とは断定できない**。TinyGo 0.42.0以降に`uefi-amd64`ターゲットがあり、現状はx86-64限定で、GCはメモリを回収しない方式、対応するUEFIサービスも限定される。通常のGo処理系とTinyGoの機能・ランタイムを混同してはいけない。[15](references.md#ref-15)[16](references.md#ref-16)[18](references.md#ref-18)

`ExitBootServices()`の前後では利用できるサービスが変化するため、OS上の一般アプリケーションとは異なる設計が必要になる。

Gooseは現在のランタイムを直接UEFI上で利用する設計ではない。Cコードを生成できるというだけでは、起動環境に依存しないことの証明にはならない。また、通常のOSユーザー空間で動作するGooseのC生成結果をクロスコンパイルできたとしても、必要なメモリマッピング、ABI、ランタイム初期化が対象環境で成立するとは限らない。

### 5.5 組込み・ベアメタル・リアルタイム

組込みLinuxならGoやRustも十分に現実的である。一方、RAMが小さいMCUやOSを持たない機器では、固定メモリ、割り込み、ハードウェアレジスタ、最悪実行時間の見積もりが重要になる。

Rustの`no_std`、ZigのFreestanding、Cは選択肢になる。TinyGoも一部のMCUに対応するが、通常のGo環境との機能差がある。いずれの言語でも、ハードリアルタイム性の成立には割り込み設計・Worst-case Execution Time (WCET)・メモリ確保方針・RTOS等を個別に検証する必要がある。[16](references.md#ref-16)

GooseはGCを持たないものの、**GCがないことはベアメタル適性やハードリアルタイム性の十分条件ではない**。現在のData Stackの予約・ページ処理モデルを再設計しない限り、OSなしの環境には向かない。

### 5.6 計算アルゴリズム、パーサー、DB

Gooseを研究する価値が特に高い分野は、短寿命の大量データを扱う処理だ。ここでは**「言語処理系の機能として適している」ことと「すぐに製品へ組み込めるライブラリがある」ことを区別**する必要がある。

- バイナリ・テキストパーサー、構文木
- 大量のレコードの生成、走査、一括解放
- コンパクトなグラフ表現、相対参照、インデックス
- シリアライズ・デシリアライズ
- 一時バッファが支配的な計算処理

反対に、頻繁な挿入・削除、複雑に交差する所有関係、巨大な共有メモリ、プラグイン動的ロードなどでは、RustやZig、C++の自由度が有利になる場合がある。

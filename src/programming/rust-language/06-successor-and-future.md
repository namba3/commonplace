## 14. RustはC言語の正統な後継候補か

ここからは仕様の紹介ではなく、言語の位置づけに関する考察である。先ほど見た「Cの皮を被ったML/OCaml」という表現を踏まえると、Rustが何を継承したのかという問いも、単なる系譜以上の意味を持つ。

「正統な後継」という言葉を、Cの構文に似ていることやCのソースコードをそのまま移植できることだと定義するなら、Rustは後継とは言いにくい。所有権、型システム、エラー処理、ビルド文化は大きく異なる。

しかし「Cが担ってきたシステムプログラミングの領域を、現代的な設計で引き継ぐこと」と定義すれば、Rustは**有力な後継候補の1つ**になる。

### 14.1 Cの本質を何と見るか

C言語の重要な特性として、次のような点が挙げられる。

- ハードウェアと比較的近い操作を表現できる。
- 管理ランタイムを必須とせずに実行できる。
- OS・組込み・ライブラリ基盤などに広く使える。
- C ABIを中心とする相互運用の蓄積がある。
- 言語とツールチェーンが多様なプラットフォームを支えている。

Rustは、これらのうち多くを別の形で引き継ぎつつ、メモリ安全性、抽象化、並行性の契約を強化している。

一方、**言語仕様が提供する保証と、長年にわたり蓄積されたCの移植性・ABI・ツール対応は別物**である。Cの巨大な資産を直ちに置換できることにはならない。

### 14.2 C/C++/Rustの比較

| 観点 | C | C++ | Rust |
| --- | --- | --- | --- |
| 主な設計の重心 | 小さい言語の中核と低水準制御 | 低水準制御と多様な高水準抽象化 | 所有権による保証と高水準抽象化の統合 |
| メモリ管理 | 手動管理が中心 | RAII・スマートポインタ等を使える | Ownership・Borrow・Drop |
| メモリ安全 | 言語全体では保証しない | 言語全体では保証しない | Safe Rustで強い保証、`unsafe`等は監査が必要 |
| 型推論 | 比較的限定的 | `auto`、テンプレート推論等 | ローカル型推論、Generics、Trait制約 |
| 抽象化 | 関数、構造体、マクロ等 | クラス、テンプレート、コンセプト等 | Trait、Generics、enum、マクロ等 |
| 関数型的表現 | 関数ポインタ等が中心 | ラムダ、Ranges等を利用できる | Closure、Iterator、パターンマッチが日常的 |
| 導入・移行 | 既存資産が非常に豊富 | 既存資産が非常に豊富 | FFI等を使い、境界を設計しながら導入 |

表は大局的な特徴の比較であり、個々のC++コードがRustコードより常に危険・低水準であることを意味しない。

### 14.3 「Cの後継」としての魅力

Rustを後継候補と見る根拠は、単にCと同程度の低水準操作ができるからではない。さらに、ML系の表現力と所有権モデルを取り込んだことで、Cの世界で当たり前だった設計上の負担を別の形に組み替えた点にある。

その中でもとりわけ重要なのが、**Cがプログラマーの規律に依存していた不変条件の一部を、コンパイラが検査可能な契約へ移したこと**である。LLVMによる高度なコード生成は、その設計を現実の低水準ソフトウェアへつなぐ実用上の強みとなる。ただしC/C++も同じLLVMバックエンドを利用でき、言語間の性能優劣をLLVM採用の有無だけで決めることはできない。

Cでは正しく書けば安全で効率的なコードを作れる。しかしRustでは、正しく書くための制約の多くを言語が明示する。さらに式志向、関数型的な合成、Traitなどの高水準な記法を、同じ言語内で利用できる。

この意味でRustは「Cの上に安全機能を貼り付けたもの」ではなく、**システムプログラミングを成立させるための契約を再設計した言語**と評価できる。

### 14.4 それでも普遍的な後継ではない

Rustがすべての場面でCを置き換えるとは限らない。

- 最小限のコンパイラやランタイム環境しか用意できないターゲットでは、Cの方が導入しやすい場合がある。
- ABI、既存のヘッダ、既存のCライブラリ、組織内のノウハウなどは長期的な資産である。
- 既存CコードをRustに書き換える費用が、リスク低減の効果を上回る場合もある。
- Rustの所有権設計や型レベルの抽象化は、実装者に大きな学習負荷を要求し得る。
- 厳密なリアルタイム制約や環境固有の事情は、言語名だけでは解決しない。

したがって、**「Cの機能的な後継候補」**という評価と、**「Cの完全な代替」**という主張は区別したい。後継と呼べるかは、言語が解決する課題に注目するのか、C ABI・ツールチェーン・ソース互換性という蓄積に注目するのかでも変わる。

## 15. Rustの難しさとトレードオフ

好意的に評価するほど、制約にも目を向ける必要がある。

### 15.1 借用検査は正しいプログラムも拒否し得る

静的解析は保守的だ。実行上は安全なはずの所有関係が、コンパイラに証明できないことがある。`Rc`、`Arc`、`RefCell`、`Mutex`、所有データへの変更、データ構造の組み直しなどで設計を変える必要もある。

これは言語の失敗というより、**事前に安全性を確認するための代償**だが、開発効率には影響する。

### 15.2 コンパイル時間・バイナリサイズ・エコシステム

豊かなGenerics、マクロ、依存クレート、LLVMを含むバックエンドの大規模な最適化にはビルド時間と保守コストが伴う。単相化は実行時性能に有利な場合がある一方、コードサイズを増やすこともある。

Web UI、GUI、組込みの領域では、プロジェクトに合うフレームワーク・ライブラリの成熟度、対象プラットフォーム、長期サポートを個別に確認しなければならない。

### 15.3 安全性は正しさ全体ではない

Rustの型検査・借用検査は、**言語と安全な抽象化が守る範囲で**メモリ上の重要な危険を排除する。しかし、不正な仕様、計算誤り、デッドロック、境界条件の見落とし、権限設計の失敗、サプライチェーンの問題は別途検証が要る。特に`unsafe`を含む依存クレートの健全性を、呼び出し側のSafe Rustだけで監査できるわけではない。

これは[AIコーディング時代の型システムと形式検証](../type-systems-and-formal-verification/)で議論した「型安全・メモリ安全・仕様の正当性は別物」という区別にもつながる。

## 16. AIコーディング時代にRustが持つ、もう1つの意味

ここは今後の展望に関する仮説である。

AIがコードを生成するとき、Rustのコンパイラは型・所有権・借用・Trait境界について、人間のレビューとは独立したフィードバックを返せる。

```mermaid
flowchart LR
    A["要求と設計"] --> B["AIまたは人がコードを作る"]
    B --> C["型・借用検査"]
    C -->|エラー| B
    C -->|通過| D["テスト・静的解析"]
    D --> E["仕様・設計レビュー"]
```

コンパイルが通ることは仕様への適合を意味しない。それでも、**生成されたコードを機械的に検証しやすい性質**は重要である。

一方、複雑な借用エラーを解決するためにAIが不必要な`clone()`、`Arc<Mutex<_>>`、あるいは`unsafe`を使えば、コードの意図や性能が損なわれる可能性もある。よって言語の有利さは、コンパイル成功率だけでは測れない。

これは既存の[AIコーディング時代のシフトレフト](../../software-engineering/ai-coding-shift-left/)で扱った、「生成より前に要求・制約・検証可能性を設計する」という立場とも整合的だ。

## 17. 総括：Rustの革新は「境界」を型で扱うことにある

Rustを特徴づける機能を1つだけ選ぶなら、所有権が有力だろう。しかし魅力の核心は、それだけではない。`let`とパターンによる束縛、`enum`と`match`、Traitと関連型、Move/Borrow、型推論が**同じコードで矛盾なく協調するよう設計されていること**にある。

その背景にはC/C++的な低水準制御、ML/OCamlのデータ表現と式志向、Haskellの型クラスを連想させる抽象化がある。Rustはそれらを単純に寄せ集めたのではなく、所有権と型システムという制約の下で組み替えた。

| 側面 | Rustが実現しようとすること |
| --- | --- |
| 束縛・Shadowing | 新しい値・パターンと名前を結び付け、再代入と区別する |
| 所有権・借用 | 誰が値を持ち、誰がいつアクセスできるかを検査する |
| ライフタイム | 参照間の有効期間の関係をAPIに表現する |
| 型推論 | 静的型の制約を保ちつつ、実装の記述を簡潔にする |
| Trait・Generics | 具体的な型に依存しない設計を表現する |
| Associated Type・GAT | 振る舞いに関連する型と、そのライフタイム等の関係を契約にする |
| 式志向・パターンマッチ | 分岐やデータ構造を値の合成として扱う |
| クロージャ・Iterator | 処理の組み合わせを宣言的に記述する |
| `Option`・`Result` | 不在と失敗を通常の値として扱う |
| `unsafe`・FFI | 低水準処理の責務を明示的な境界へ閉じ込める |
| LLVMを中心とするコード生成基盤 | 高水準な表現から最適化されたターゲットコードへの橋渡しを担う |
| Cargoと周辺ツール | 多分野での実用的な開発を支える |

この表の共通項は、単純な「安全性」でも「高速性」でもない。**抽象化と制約を別々の層へ追いやらず、言語の中で組み合わせていること**だ。LLVMという成熟したバックエンドは、その表現を現実的なターゲットコードへ変換するための強力な基盤になる。

その根底にある発想を一言で表せば、**値・状態・アクセス権・リソース・抽象化の境界を、できるだけコンパイラに理解可能な形で表現すること**だろう。

Rustは、その制約を受け入れることで、高水準な記法と低水準な制御を同居させようとしている。これは美点であると同時に、借用検査や型システムの学習コストが生じる理由でもある。

この意味でRustは、「Cをメモリ安全にした言語」にとどまらない。**Cが切り開いたシステムプログラミングを、ML系の表現力と現代的な型・所有権の制約によって再構成した言語**と評価できる。

ただし、RustをCの「正統な後継」と呼ぶかどうかは評価基準による。豊富なC資産の移行コストや、限定された環境での移植性まで消えるわけではない。**有力な後継候補の1つ**という評価に留めるのが妥当だろう。

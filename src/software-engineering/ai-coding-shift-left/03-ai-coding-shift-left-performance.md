# Performance by Design：AIが書くコードの性能を設計段階から考える

動くコードをAIが生成したあと、ベンチマークで「遅い」と判明したら改善すればよい――という考え方には限界があります。全件ロードや無制限の並列実行のように、**性能問題の原因がアルゴリズムや構造そのものにある場合**、後からの局所最適化では済まないからです。

この記事は連載の中でも技術的な深掘り回です。性能要求、モデル化、性能予算、Rust製ファイルマネージャーの例、実測とCIの設計までをまとめます。


> **注記**
> 記事中の性能数値や容量は説明用の仮値であり、推奨される一律の基準ではありません。


## Performance by Designとは何か

**Performance by Design** は、性能を完成後の「高速化」で取り戻すものではなく、**要求定義・モデル化・アーキテクチャ・アルゴリズム・検証・運用を通じて意図的に成立させる品質属性**として扱う設計思想です。あらゆる処理の最速化を目指すのではなく、想定する負荷・利用者体験・資源制約のもとで必要な性能を維持します。

関連する歴史的背景には、Connie U. Smith の *Performance Engineering of Software Systems*（1990）に代表される **Software Performance Engineering（SPE）** と、Menascé・Almeida・Dowdy による *Performance by Design: Computer Capacity Planning by Example*（2004）がある（[Smith (1990)](https://books.google.com/books/about/Performance_Engineering_of_Software_Syst.html?id=q8omAAAAMAAJ)、[Menascéら (2004)](https://books.google.com/books/about/Performance_by_Design.html?id=sxE931Medm4C)）。したがって、AIコーディング固有の新概念でも、統一された唯一の標準規格でもありません。本記事では、性能工学をAI支援開発へ応用する方法を整理します。

シフトレフトとの接点は次の三層として把握できる。

| 層 | 目的 | 具体的な活動 |
|---|---|---|
| **予防（設計）** | 後で直しにくい性能リスクを減らす | 負荷条件、計算量、データフロー、並行処理境界を設計 |
| **早期検証** | 危険な仮説を安価に反証する | モデル、プロトタイプ、局所ベンチ、設計レビュー |
| **継続的検証** | 改変による性能回帰と環境変化を把握する | E2E負荷試験、ベースライン比較、運用観測 |

**シフトレフトは「品質活動をいつ始めるか」、Performance by Designは「性能を何に基づいて成立させるか」に重点がある。** 両者は補完関係にあり、実負荷の継続測定を置き換えない。Microsoft Azure Well-Architected Framework でも性能目標の早期定義、容量要件を満たす設計、定期試験・継続監視を扱っています（[Microsoftの設計原則](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/principles)）。

## 後付け最適化と設計上の性能対策

| 観点 | 後付けの局所最適化に偏る場合 | Performance by Design |
|---|---|---|
| 要求 | 完成後に「遅い」と判明 | 重要なシナリオと負荷を先に特定 |
| データ構造 | 動作するものから採用 | 読み書き比率、規模、メモリから選択 |
| アルゴリズム | 実測後に全体を組み替える | 計算量と境界条件を設計時に比較 |
| I/O・UI | 一括処理・同期処理が既定になりがち | 増分処理、仮想化、非ブロック化を検討 |
| 検証 | リリース直前の単発測定 | 小さなPoCから本番観測まで継続 |

ここでの対比は説明用であり、後からの最適化が不要という意味ではない。むしろ、**変更しづらいマクロな構造を早期に検討し、ミクロな最適化は測定結果に応じて実施する**のが基本です（[Knuthの議論](https://doi.org/10.1145/356635.356640)も参照）。

## 「性能」は処理速度だけではない

| 観点 | 代表指標 | 設計上の主要な問い |
|---|---|---|
| レイテンシ | 平均、p95、p99、最大値 | クリティカルパス・待機・同期I/Oは何か |
| スループット | req/s、件/s、MiB/s | 並列性・バッチ化・競合の制約は何か |
| UI応答性 | 入力遅延、フレーム時間、フリーズ時間 | メインスレッドに重い処理を載せていないか |
| リソース効率 | CPU、メモリ、GPU、I/O、通信 | コピー・アロケーション・データ移動は適切か |
| スケーラビリティ | データ量・接続数に対する性能曲線 | 件数増加で何が飽和するか |
| 持続性能 | 長時間負荷時の劣化、ピーク使用量 | リーク、熱、キャッシュ、断続的負荷の影響は何か |
| コスト・電力 | 仕事量当たりの費用・消費電力 | 速度向上に必要な資源増加は妥当か |

**速いことと効率が良いことは異なります。** 並列度を増やしてレイテンシを下げても、ピークメモリや電力、運用費が増える場合があります（[性能と他品質とのトレードオフ](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/tradeoffs)）。

## 測定可能な性能要求と負荷モデル

「高速で軽量」では合否を判定できない。少なくとも、**操作・入力規模・同時負荷・ハードウェア・ビルド設定・キャッシュ状態・指標・許容値**を指定する。

| 対象 | 仮の受入条件 | 測定条件・注意点 |
|---|---|---|
| アプリ起動 | 利用可能になるまでp95 ≤ 500ms | 指定検証PC、コールドとウォームを別集計 |
| UI入力 | 入力から描画反映までp95 ≤ 100ms | 通常時・バックグラウンド負荷時を区別 |
| 大規模一覧 | 10万件でもUI操作を継続可能 | 初期表示・全件列挙・スクロールを別指標にする |
| メモリ | 代表操作でピーク ≤ 200MiB | データセットと計測範囲を固定 |
| バッチ処理 | 所定件数を所定時間以内 | CPU・ストレージ・並列数を固定 |

**上記の数値はすべて説明用の仮値であり、推奨標準値ではない。** 性能目標は、実際の利用者体験や事業要件と整合させて決める。平均だけでは遅い一部のリクエストが見えにくいため、必要に応じてp95/p99、最大待機時間、エラー率なども扱う。

## アルゴリズム・データ構造・システム構造

たとえば100万件のキー検索を考える。理論計算量だけで最適な解を確定することはできないが、設計段階で候補の危険性を絞り込める。

| 手法 | 代表的な検索コスト | 追加の検討事項 |
|---|---|---|
| 線形走査 | `O(n)` | 小規模や高いメモリ局所性では有利な場合もある |
| ソート済み配列の二分探索 | `O(log n)` | 更新・挿入コストとソートの維持 |
| ハッシュテーブル | 平均的に `O(1)` | メモリ、ハッシュ計算、最悪時の振る舞い |
| 平衡木などの索引 | 典型的に `O(log n)` | 範囲検索、更新コスト、ノード配置 |

アルゴリズム以外にも、次の構造を優先的に確認する。

- **I/Oとデータ移動**：不要な全件ロード、繰り返し走査、シリアライズ、メモリコピー。
- **クリティカルパス**：ユーザー応答を遅らせる同期処理と直列依存。
- **並行処理**：同時実行数、有界キュー、バックプレッシャー、タイムアウト、キャンセル。
- **キャッシュと索引**：利得だけでなく更新費用、鮮度、整合性、メモリ上限。
- **拡張性**：入力規模や同時実行数が増えた際の飽和点と縮退時挙動。

## 数理モデルによる早期の設計検証

モデルは設計を保証する魔法ではないが、不可能な期待や明らかな構造的制約を早期に発見できる。

| モデル | 用途 | 限界 |
|---|---|---|
| 計算量解析 | 規模増加による処理量の増え方 | 定数・メモリ局所性・実装差は分からない |
| Amdahlの法則 | 固定ワークロードでの並列化限界 | 競合・同期・スケジューリング等を理想化 |
| Littleの法則 | 平均系内件数と処理量・滞留時間の関係 | 定常状態・長期平均を前提とする |
| 待ち行列モデル | 負荷集中と待ち時間の関係 | 到着率・サービス時間の仮定に依存 |
| Rooflineモデル | 演算量とメモリ帯域の相対的制約 | 数値計算・GPU処理で特に有用 |

Amdahlの法則（逐次割合`s`、並列数`p`の理想化モデル）：

\\[
S(p)=\frac{1}{s+(1-s)/p}
\\]

Littleの法則（安定した系の長期平均）：

\\[
L=\lambda W
\\]

平均100件/秒、平均滞留時間0.2秒であれば、平均系内件数は20件となる。**予測値には仮定と適用範囲を必ず残し、PoCや実測で更新する。**

## Performance Budget（性能予算）

全体の制約をコンポーネントやクリティカルパスへ配分する。例として、完全に直列なUI操作のレイテンシを100msと仮定する。

| 処理段階 | 仮の予算 |
|---|---:|
| イベント処理 | 10ms |
| データ処理 | 30ms |
| 状態更新 | 20ms |
| 描画・反映 | 40ms |
| **合計** | **100ms** |

これは**説明用の直列モデルであり、各工程のp95の単純和で全体のp95を求められるわけではない**。並列・非同期処理、OSやGPUの待ちを含む現実のクリティカルパスに沿って予算を設定し、全体のE2Eレイテンシを別途測る。

予算はレイテンシだけでなく、CPU、ピークメモリ、I/O量、ネットワーク量、電力、処理単位当たりの運用費にも設定できる。予算は責任境界や優先順位を議論する道具であって、個別予算を満たせばシステム全体が自動的に合格する保証ではない。

## ケーススタディ：Rust製デスクトップファイルマネージャー

**要求例**：10万件規模のディレクトリを開いても、UIの操作性を維持する。

問題のある設計では、全件列挙→全件メタデータ取得→全件ソート→全件Widget構築をUIの表示前に逐次実行しがちである。設計段階から次を選択肢として検討する。

| リスク | 初期設計の候補 | 確認すべきトレードオフ・検査 |
|---|---|---|
| 初期表示が遅い | 増分列挙、分割通知、遅延メタデータ取得 | 初期表示と全件完了を別測定、並び順の仕様 |
| Widget生成負荷 | 仮想リスト、可視範囲中心の更新 | スクロール時フレーム時間・ピークメモリ |
| UIスレッドが停止 | ワーカー・非同期I/O・中断可能な処理 | フリーズ、キャンセル、競合時の応答性 |
| タスク数の爆発 | 有界キュー、同時実行制限 | 高負荷時のメモリ、待機、キャンセル挙動 |
| 古い結果が新画面を上書き | 世代識別子などによる結果棄却 | ディレクトリを素早く切り替えるテスト |
| 検索・ソートが重い | 用途に応じた索引・段階的処理 | 更新費用、整列順の一貫性、正確性 |

段階的に1千、1万、10万件を試し、SSD・HDD・ネットワーク共有などI/O条件が違う環境も考慮する。**初回表示・全件列挙完了・正しい整列順・スクロール応答性は別々の要求**であり、同時に無条件で改善できるとは限らない。

## 検証レイヤーと測定の再現性

| 検証レイヤー | 目的 | 例 |
|---|---|---|
| マイクロベンチ | 局所的なアルゴリズム比較 | 索引、パーサ、シリアライズ |
| コンポーネント試験 | モジュールの処理特性 | 列挙、検索、描画更新 |
| E2E計測 | 利用者に届く性能 | 起動、一覧表示、検索完了 |
| 負荷・ストレス試験 | 飽和点、過負荷時の劣化 | 同時要求、待ち行列、最大メモリ |
| 長時間試験 | リークや蓄積劣化 | 連続操作、長時間アイドル |
| 運用観測（Shift Right） | 想定と実利用の差 | 実負荷の分位点・資源使用・エラー率 |

測定時は**測定環境（CPU・OS・ストレージ・電源設定）、Release/Debug、入力データ、コールド/ウォームキャッシュ、反復回数、ばらつき**を明示する。環境差やノイズの範囲内の小差を「改善」と言い切らない。マイクロベンチの改善をE2E改善の証拠にすり替えない。

CIの性能ゲートは、安定した軽量測定をPR単位で、重い実負荷試験を定期またはリリース前に分ける。閾値は過去のばらつきや実害に基づいて選ぶ。**計測未実施は合格ではなく未検証**と記録する。

## Premature Optimizationと品質のトレードオフ

構造的な問題（`O(n^2)`の不適切な採用、巨大リストの全件描画、無制限のキューなど）を早期に検討することと、実測根拠なくループ展開や手動SIMDを施すことは別です（[Knuthの原論文](https://doi.org/10.1145/356635.356640)）。

| 性能改善策 | 利点 | 代償・他品質への影響 |
|---|---|---|
| キャッシュ | 再計算・再取得を減らす | 鮮度・無効化・メモリ |
| 並列化 | スループット向上の余地 | 競合・同期・再現性・電力 |
| バッチ化 | 呼び出し・I/O回数の削減 | 個々のリクエストの待ち時間 |
| 遅延ロード | 初期応答の改善 | 後続操作でのI/O・UX複雑化 |
| 事前計算・索引 | 照会高速化 | 構築・更新費用・整合性 |

性能の局所最適化が正確性、セキュリティ、保守性を破壊してはならない。妥当な設計は、目標と優先順位、採用しなかった案、実測結果をADRなどに残す（本記事末尾のレビュー項目とADR例を参照）。

## AIエージェントにおける性能設計の分業

| 工程 | AIに任せやすいこと | 人間・独立した検証が担うこと |
|---|---|---|
| 要求 | 性能指標、負荷条件、リスクの候補を洗い出す | 目標が利用者価値や事業制約に合うか決定 |
| 設計 | 代替案、計算量・資源コストの仮説を比較 | 境界・トレードオフ・高リスク判断を承認 |
| 実装 | 設計制約に沿って段階的にコードとテストを生成 | 設計逸脱や抜けを確認 |
| 検証 | ベンチ・負荷試験を作り、結果を集計 | 実験条件、期待値、統計的ばらつきを点検 |
| 改善 | プロファイル結果から改善案を示す | 実測で改善を再確認し、複雑化の妥当性を判断 |

**「高速に実装して」ではなく、「どの負荷で、何を、いくつ以下／以上にし、何で検証するか」を指示する**。AIの性能予測は仮説であり、ベンチマーク未実施なら「性能改善済み」とは報告させない。

## 性能ゲートを作るなら「測定の信頼性」も設計する

たとえば初期表示時間を20回だけ測ってp95を比較しても、その差が測定環境の揺らぎか実装改善かは慎重に判断する必要があります。サンプルを増やし、複数回の実行、基準実装との比較、測定日の違いも含めて確認します。**p95の推定値と、目標を満たす確信度は別物**です。


### 小さな測定例：p95をどう読むか

仮に、同じ条件で初期表示時間を**20回ずつ**記録したとします。ここでは説明のために作った架空のデータであり、実際のベンチマーク結果ではありません。昇順の20個から最も単純なnearest-rank法でp95を取ると、19番目（`ceil(0.95 × 20)`）の値になります。

| 仮の実装 | p95（20回の標本） | 重要な読み方 |
|---|---:|---|
| 全件処理型 | 184ms | 19番目の記録値 |
| 増分処理型 | 121ms | 同一条件での比較という仮定 |


### 説明用の20サンプル（ミリ秒、昇順）


- 全件処理型：`112, 113, 116, 118, 123, 125, 129, 130, 132, 138, 140, 145, 150, 154, 160, 165, 170, 178, 184, 230`
- 増分処理型：`65, 68, 70, 72, 75, 77, 79, 81, 84, 86, 89, 92, 94, 96, 100, 103, 108, 114, 121, 155`



数値上は後者が有利に見えますが、**20サンプルのp95は少数の観測値に強く左右されます**。分位点の定義（補間など）によって値が異なる場合もあります。これだけで「性能目標を安定して達成した」「一般に高速になった」と結論づけず、分布、反復、測定条件、用途に応じた不確実性を確認します。

特にp95やp99は、単に1回の測定結果から断言するものではありません。評価対象となる操作、試行回数、ウォームアップ、異常値の扱い、ハードウェアとOSの条件、リビジョンを記録します。

性能比較では、局所ベンチで5%改善してもユーザー体験が5%改善したとは限りません。**全体のE2E測定を先に成功指標に据え、局所測定を原因分析に使う**と考えるのが安全です。

PRで走らせるベンチマークが環境ノイズで頻繁に失敗するなら、最初からBlockingにせずAdvisoryにし、安定した専用環境や定期測定で判定の確度を上げる方法もあります。


### 性能設計レビューのチェック項目


通常の設計レビューに追加する性能固有の項目。**性能が重要な課題に重点適用し、L0の軽微な変更へ一律適用しない。**

**要求・モデル**

- [ ] 性能が重要なユースケースと利用者体験を特定した。
- [ ] 典型負荷・ピーク負荷・入力規模・同時実行数を区別した。
- [ ] レイテンシ、スループット、ピークメモリなどの目標を、測定環境つきで定義した。
- [ ] 計算量・I/O・メモリ・データ移動・クリティカルパスを概算した。
- [ ] 性能予算に仮定と責任境界を記載した。

**アーキテクチャ・実装前**

- [ ] 不必要な全件処理、同期I/O、コピー、競合を生む構造を点検した。
- [ ] 同時実行数・キュー長・キャッシュ容量の上限を検討した。
- [ ] キャッシュ・索引・バッチ化の更新費用と整合性を検討した。
- [ ] 後から変更しにくい判断を特定し、必要ならADRと代替案を残した。
- [ ] 不確実性が高い主要性能仮説を、実装前のPoCや局所ベンチで検証した。

**検証・運用**

- [ ] マイクロベンチだけでなく、重要なE2Eシナリオを測定した。
- [ ] データセット、ハードウェア、ビルド、キャッシュ条件、反復測定の情報を保存した。
- [ ] 基準値とばらつきを考慮して性能回帰を評価した。
- [ ] CIでの軽量試験と、定期・リリース時の重い負荷試験を使い分けた。
- [ ] 未測定・未達・達成を区別し、残留リスクを課題表へ戻せる。
- [ ] 実運用の測定結果を初期モデル・受入基準・設計判断に反映できる。




### 性能設計のADRに残しておきたいこと


以下は、一般的なADRを性能に関わる判断へ特化させた例です。**同じ決定についてADRを二重作成せず、既存のADRへ項目を追加してもよい。**

```markdown
# ADR-XXXX: <性能に関わる設計判断>

- 状態：proposed / accepted / superseded
- 関連課題の正本ID：

## 性能要求・負荷条件
- 対象ユースケース：
- 目標指標・閾値：
- 典型負荷／ピーク負荷：
- 検証環境・データセット：
- 守るべき他の品質条件：

## 設計案
| 案 | 計算量・I/O・メモリ特性 | 長所 | 短所・リスク |
|---|---|---|---|
| A | | | |
| B | | | |

## 選択と理由
- 採用案：
- 判断根拠：
- 非採用案と理由：
- 後から変更しにくい構造上の決定：
- 正確性・安全性・保守性とのトレードオフ：

## 検証
- 実装前に試すPoC／性能仮説：
- 実装後のベンチ／E2E計測：
- ベースライン：
- 合格基準・許容変動：
- 測定結果：未測定
- 統合・運用でしか分からない事項：

## 再検討条件
- 利用規模・性能指標の変化：
- 実運用の観測項目：
- 設計を見直す条件：
```



## まとめ

**マクロな性能特性は設計し、ミクロな最適化は測定する。** 計算量や待ち行列のモデルは性能を保証する魔法ではありませんが、生成前に危険な仮説を絞り込めます。AIには単に「速くして」ではなく、**対象負荷・性能予算・計測環境・合格基準**を渡すのが重要です。

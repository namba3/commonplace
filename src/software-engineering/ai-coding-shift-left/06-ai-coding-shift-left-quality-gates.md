# AIコーディングの品質ゲート：リスク分類・CI・承認をどう設計するか

作成日：2026-10-12 / 更新日：2026-10-12

AIコーディングに品質ゲートを導入する際、`AGENTS.md`に「必ずテストせよ」と書くだけでは十分ではありません。テストが失敗してもマージできるなら、そのルールは**実際には強制されていない**からです。

この回では、変更リスクに応じてレビューの重さを変える方法、CIと承認権限の分離、品質ゲートそのものの検証を考えます。


> **注記**
> 以下のL0〜L3は連載独自の説明用モデルであり、認証された標準や万能のリスク計算式ではありません。法令、組織規程、既存のブランチ保護を優先してください。


## 変更リスクと承認責任

### リスクは「最も高い該当条件」で暫定分類する

ここでのL0〜L3は**本連載の運用例**であり、業務リスクに応じて上書きする。行数や実装難度ではなく、被害の大きさ、影響範囲、可逆性、外部公開性、不確実性で評価する。迷った場合は低く見積もらず、必要な調査を先に行う。

| レベル | 判断例 | 設計レビュー | 最小の検証・承認 |
|---|---|---|---|
| **L0 軽微** | 明確な文言修正、影響の限定された表示調整 | 既存仕様確認 | 影響箇所の確認、通常の保護ルール |
| **L1 通常** | 局所機能追加、後戻りしやすい内部処理 | 受入条件、影響範囲 | 関連テスト、通常レビュー |
| **L2 高リスク** | 認可境界、データ形式、主要性能経路、競合制御、公開API | 代替案・異常系・必要ならADR/PoC | 専門観点のレビュー、広い回帰・必要な重点試験 |
| **L3 重大** | 大規模データ消失の恐れ、不可逆な外部操作、決済・安全性重要機能 | 正式なリスク受容・復旧計画・場合によって脅威分析 | 独立した承認、段階公開・復旧検証・監視 |

### 判定フローと昇格条件

```text
1. 損害・規制・事業上の影響が重大、または安全性重要か？ ─ yes → L3候補
2. 信頼境界、永続化、公開互換性、不可逆操作、並行性、
   性能重要経路、unsafe/FFI、特権処理などを変更するか？ ─ yes → 原則L2以上
3. 局所的・可逆的で影響範囲を把握できるか？ ─ yes → L0〜L1候補
4. 前提・影響範囲・復旧可能性が不明か？ ─ yes → 暫定分類を保留して調査
5. 複数条件に該当したら、最も高いリスクで扱う
```

条件2は**自動的にすべてL2と確定する規則ではなく、昇格して評価すべきトリガー**である（例：`unsafe`のコメント修正はコード変更と区別する）。不明点が解消するまで、低レベルを根拠に必須検査を免除しない。リスクは実装中の発見で引き上げられ、必要な検証を再設定する。

### 誰が何を承認するか

1人が複数の役割を兼務する小規模開発でも、**活動と権限を論理的に分けて記録する**。L2/L3で必要な「独立レビュー」は、プロジェクトの人員・リスクに応じて別担当者や外部レビュー・自動検査などを組み合わせるが、自己承認を独立レビューと称しない。

| 判断対象 | 草案・実行 | 最終的な責任者（例） | 証拠／権限境界 |
|---|---|---|---|
| 要求の目的・妥当性 | AI・開発者・利用者 | 機能オーナー／依頼者 | VAL結果、受入条件の承認 |
| 構造上の高リスク設計 | AI・実装者 | 設計責任者または指定レビュアー | ADR・リスク評価・代替案 |
| 検証基準の変更 | AI・実装者 | 要求責任者／品質責任者 | 変更理由と期待値差分 |
| 品質ゲートの例外 | 変更担当者 | ポリシー上の例外承認者 | 期限・代替統制・追跡課題 |
| マージ・リリース | CI・AIが補助 | 保護ルールで認められた人／仕組み | CI、承認、リリース記録 |

**AIの提案・実行権限は承認権限ではない。** L3や法令に関わる変更は、組織の正式な役割分担がこの表より優先する。

## 品質ゲートを「宣言」で終わらせない

### BlockingとAdvisoryを分ける

| ゲート | 例 | 位置づけ |
|---|---|---|
| 基本品質 | コンパイル、型検査、フォーマット、lint | 通常はBlocking |
| 機能品質 | 単体・契約・主要統合テスト | 変更範囲に応じてBlocking |
| セキュリティ | 重大な秘密情報漏洩、既知の重大脆弱性 | ポリシーに応じてBlocking |
| 構造品質 | 禁止依存、循環依存、公開API破壊 | 重大な逸脱はBlocking |
| 性能 | ノイズ制御された主要性能回帰 | 測定環境に応じてBlockingまたはAdvisory |
| 重い試験 | 長時間負荷、E2E、障害注入 | 定期実行またはリリースゲート |

**不安定な性能ベンチマークを無条件にPRの必須ゲートとすると、誤検知で開発を止める。** 判定の信頼性も設計対象とする。

### リスク別の最低ゲート例

| ゲート | L0 | L1 | L2 | L3 |
|---|---|---|---|---|
| 変更に関連するビルド・静的検査 | 原則必須 | 必須 | 必須 | 必須 |
| 受入条件に直結するテスト | 該当時 | 必須 | 必須 | 必須 |
| 設計・差分レビュー | 軽量 | 通常 | 重点・必要ならADR | 指定独立レビュー |
| セキュリティ・性能・移行の重点試験 | 該当時 | 該当時 | リスクがあれば必須 | リスクに沿って必須 |
| 復旧手順・段階公開 | 通常不要 | 該当時 | 必要時 | 原則として計画と検証が必要 |

これは**ポリシー設計例であり、現在のCIへ自動適用される設定ではない**。実際のBlocking判定はブランチ保護・ジョブ設定・権限規則で強制する。

### PASSと未検証を混同しない

判定は最低限 `PASS / FAIL / NOT_RUN / INCONCLUSIVE` を区別する。`INCONCLUSIVE` は計測ノイズやテスト環境不調などで合否が決められない状態を指し、`PASS`ではない。`SKIP`も理由つきの未実施として扱う。

**BlockingゲートがFAILしたまま例外を認める場合**は、少なくとも「対象・理由・残留リスク・代替統制・承認者・期限・再検証条件」を記録する。重大な秘密漏洩やデータ消失などは、単純な例外承認で通してよいとは限らない。判断は組織のポリシーと法的要件を優先する。

| 状態 | 通常の扱い | 必須の記録 |
|---|---|---|
| PASS | 次の工程へ進める | 実行条件・ログ／CI ID |
| FAIL | Blockingなら統合を止める | 失敗原因・修正課題 |
| NOT_RUN | 合格に読み替えない | 未実施理由・実行予定または例外 |
| INCONCLUSIVE | 再測定・環境修正を検討 | 不確定要因・暫定リスク |

### 例外は期限つきのリスク受容として扱う

1. 対象ゲートと状態（`FAIL` / `NOT_RUN` / `INCONCLUSIVE`）を明示する。
2. 影響・原因・代替統制・再検証条件・期限・責任者を記録する。
3. 例外承認の権限を持つ人が承認するまで、必須ゲートを通過したことにしない。
4. 期限を自動検知できる運用を目指す。期限到来時は責任者が残留リスクを再評価し、未解消なら統合・リリース可否を改めて判定する。
5. 秘密情報漏洩、重大な不可逆損害、法令違反など、**免除不能**と定めたゲートは例外承認の対象にしない。

**運用上の注意**：テストを`skip`する、期待値を変更する、タイムアウトを緩める、CIジョブを外す操作は、単なる実装修正ではなく**検証ルールの変更**としてレビューする。

### 完了の定義（Definition of Done）

変更を完了とするには、少なくとも次を確認する。

- 受入条件が満たされ、検証証跡がある。
- 設計方針・既存の境界を破っていないか、逸脱理由が記録されている。
- 指定されたテスト・静的解析が成功している。未実施・未確認は成功と表現しない。
- 性能・安全性・互換性上の残留リスクが明示されている。
- 必要なドキュメント・課題表・ADRが更新されている。
- リリース後に追跡すべき項目は管理対象になっている。

### PR・定期・リリース・運用の検証

CIを全部PRごとに回すのではなく、**判定の速さ・信頼性・実環境への近さ**に応じて分ける。

| タイミング | 優先する検証 | 判定方針 |
|---|---|---|
| 変更中・PR | フォーマット、型検査、静的解析、関連テスト、重要な契約テスト | 短く再現性の高いBlockingを中心にする |
| 定期・夜間 | 広い統合試験、負荷・長時間試験、依存分析 | 結果を追跡し、重要な失敗は次のリリースを止める |
| リリース前 | 本番相当条件、移行・復旧、性能・セキュリティ重点検証 | 対象リスクに基づき正式な承認を行う |
| リリース後 | エラー率、遅延分布、資源使用、利用者影響 | SLO等と照合し、異常を課題へ戻す |

Rustのワークスペースなら、例えば以下を**プロジェクトのtoolchain・対象クレートに合わせて調整したうえで**使える。

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --all-targets
```

これらはビルド・静的解析・テストの一部を確認するコマンド例であり、セキュリティ・UI・性能・実環境互換性の保証を意味しない。ツール未導入・プラットフォーム差・失敗がある場合はその事実を記録し、**CI上の実行結果をAIの文章上の自己申告より優先する**。

### 実際に強制するための最小確認

`QUALITY_GATES.md`に「必須」と書くことはCIの設定変更を意味しない。必須ゲートを自動強制する場合は、**保護されたブランチの必須ステータスチェック、レビュー要件、実行者の権限、CI定義の変更権限**を対応づける。サンプルの`cargo`コマンドだけではL2/L3の独立承認や性能試験を強制できない。ゲートがまだ未実装なら**Advisory／未実装**と明記して改善課題にする。

## Policy・Enforcement・Governanceを分ける

| 層 | 役割 | 具体例 |
|---|---|---|
| Policy | 守るべき規則を定める | L2変更は設計レビューと指定テストが必須 |
| Enforcement | 規則を機械的に強制する | 必須CI、ブランチ保護、権限・レビュー要件 |
| Governance | 規則の例外や責任を管理する | 例外承認、期限、残留リスクの再評価 |

たとえば「例外が期限切れなら自動的に再評価する」という文章は不正確です。**期限切れを通知・検出する仕組み**と、**そのリスクを誰が再承認するか**は別です。自動化がないなら、未実装の規則として扱います。

## GitHubで「未実施を合格にしない」ための注意点

GitHubの必須チェックは、単に`success`だけを要求する仕組みではありません。公式ドキュメントでは、**`success`・`skipped`・`neutral`は必須ステータスチェックの許容状態**とされています（[GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)）。

一方、**ワークフロー全体がパスフィルター等でスキップされた場合は、関連チェックがPendingに残ってマージを止める場合**があります。また、**ジョブの条件分岐（`jobs.<job_id>.if`）でスキップすると成功扱いになり得ます**（[GitHub Docs: Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)）。この違いに注意してください。

| 状況 | 起こり得ること | 対策 |
|---|---|---|
| 必須ジョブを`if:`でスキップ | 成功扱いになり、検査なしで通過 | 必須ジョブ自体は常時実行し、内部で適用可否を明示的に判定 |
| パスフィルターで必須ワークフローをスキップ | Pendingのままマージできない | 必須ワークフローには不用意なフィルターを設定しない |
| 依存ジョブが先に失敗し、必須ジョブが実行されない | スキップによって意図しない判定 | `needs`と`always()`の挙動を確認し、必須ジョブを検証 |
| 実装AIがCI設定を弱める | 緑色のチェックでも検査範囲が縮小 | ワークフロー変更をコードオーナー等のレビュー対象にする |

**GitHub上のチェック状態と、本連載の`PASS/FAIL/NOT_RUN/INCONCLUSIVE`は別の体系**です。プロジェクト独自の「未検証」を許容しない要件は、ゲートジョブの実行内容とブランチ保護・ルールセットの組み合わせで実現します。

実行できる最小のGitHub Actions例は[リポジトリへの導入](./07-ai-coding-shift-left-practice.md)の章で紹介します。

### ゲートの有効性をテストする（Gate Validation）

1. テスト用ブランチで意図的に失敗するテストを追加する。
2. 必須CIが失敗し、保護対象ブランチへマージできないことを確認する。
3. 必須の承認を欠いたPRが拒否されるかを確認する。
4. 必須ジョブを条件分岐でスキップした場合にも、意図したポリシーが破られないことを確認する。
5. CI設定やテストの無効化に適切なレビューが必要か確認する。
6. 例外・期限切れ・未実行の場合の扱いを検証し、根拠を記録する。


> **注意**
> テストのために本番ブランチや本番データへ危険な変更を加えないでください。専用の検証ブランチ、保護ルールのテスト環境を使います。


### 第5・7回のサンプルを使ったゲート検査

第5章のテストをCargoクレートの`tests/view_guard.rs`に置き、第7章の`rust-ci`ジョブで実行する例なら、次の点を検証できます。

1. `complete()`の世代チェックを**検証用の別ブランチで意図的に削除**し、AC-01/AC-02テストが失敗するか。
2. その失敗が`rust-ci`の失敗となり、リポジトリのRulesetでRequired status checkに指定していればマージが阻止されるか。
3. ワークフロー・テスト・期待値の変更が、必要なレビューを経ずに取り込まれないよう保護されているか。

**コードのテスト合格と、ブランチ保護の有効性は別々の確認です。** 検証用の差分を本番ブランチへマージしてはいけません。

## 証跡と承認の境界

自動テストのPASS、設計責任者の承認、マージ権限は異なる事実です。たとえば「マージ時点のコミットSHA・必須ジョブの結果・レビュー時点の差分」を対応づけ、追加変更でレビューが失効するような運用を検討します。

**AIエージェントにコード変更を許可することと、品質ゲートを無効化したり自分でマージを承認できることは同義ではありません。**

## まとめ

品質ゲートは「緑色のCIを表示する仕組み」ではなく、**どのリスクにどの検査を必須とし、失敗・未検査・例外をどう扱うかを実際に制御する仕組み**です。ポリシーだけでなく、実効性を検証するところまで設計します。

# Security・Reliability・UI/UX by Design：品質を後付けにしない設計

作成日：2026-10-12 / 更新日：2026-10-12

「By Design」を性能だけに限定する必要はありません。性能が良くても認可を迂回できるAPI、安全でも停止したまま戻らないUI、障害から復旧できない処理は、完成したソフトウェアとしては不十分です。

この回では、品質を**後からのチェック項目**ではなく、**アーキテクチャの制約・受入条件・検証方法**へ変換するための考え方を整理します。

## 「By Design」は共通する設計の姿勢

この記事では、`X by Design` を「品質属性Xを、完成後の検査対象だけでなく、初期からの設計制約・設計判断・検証可能な要件として扱う」という**共通の発想**として使います。列挙した名称すべてが、標準化された独立手法という意味ではありません。

| 品質属性 | 事前に定義・設計すること | 代表的な検証 |
|---|---|---|
| **Correctness by Design** | 不変条件、入力・出力契約、境界条件、状態遷移 | プロパティテスト、契約テスト、形式検証（適用可能な部分） |
| **Security by Design** | 信頼境界、認可、秘密情報、脅威モデル、供給網 | 脅威レビュー、SAST、依存関係分析、動的検証 |
| **Performance by Design** | 負荷モデル、計算量、I/O、メモリ、性能予算 | マイクロベンチ、E2E計測、負荷・長時間試験 |
| **Reliability by Design** | リトライ、冪等性、タイムアウト、バックプレッシャー、復旧 | 障害注入、再試行試験、復旧試験 |
| **Maintainability by Design** | モジュール境界、責務、依存方向、拡張点 | 設計レビュー、依存分析、変更影響の検査 |
| **Usability / Accessibility by Design** | ユーザー操作モデル、キーボード操作、状態表示、アクセシビリティ要求 | UI試験、アクセシビリティ検査、ユーザーテスト |
| **Observability by Design** | ログ、メトリクス、トレース、障害の切り分け | 監視項目の検証、障害調査演習 |
| **Data Integrity by Design** | データ制約、移行、永続化、整合性、復旧 | 移行試験、プロパティ試験、復旧試験 |

品質にはトレードオフがあります。たとえばキャッシュは性能に寄与するが、データ整合性や保守性に負担を生む。**すべての品質を無制限に最大化するのではなく、優先順位と制約を決める。**

### ケーススタディ：ファイル転送中に通信が切れたら

例えば「別PCへファイルを送る」機能をAIに依頼する場面を考えます。正常に転送できるコードだけなら生成できても、通信断や再接続、転送先の権限といった要求を後から追加すると、プロトコルやUI状態管理を設計し直すことになります。

設計前に次の受入条件を置きます（説明用の例です）。

| 観点 | 実装前に合意する条件 | 主な検証方法 |
|---|---|---|
| セキュリティ | 許可していない端末から転送要求を受け付けない | 未認証・無権限の要求を拒否する統合試験 |
| 信頼性 | 通信断で不完全ファイルが完成品として公開されない | 転送中断・再送・ディスク満杯の障害注入 |
| UX | 中断時に進捗・失敗理由・再試行方法を示す | 画面状態のレビュー、ユーザー操作試験 |
| データ整合性 | 再試行しても既存の完成ファイルを破壊しない | 同一操作の再実行とハッシュ照合 |

**「送れること」より先に「何が起きても破ってはいけない条件」を合意する**のが、品質属性を設計へ取り込むという意味です。

### 設計上の推定と保証の水準

`Design by Contract` における事前条件・事後条件・不変条件は、明示された条件に対する論理的な振る舞いを扱う。一方、p95レイテンシのような性能要求は、**指定された負荷と測定環境の下で統計的に評価する非機能要件**であり、同じ意味の数学的契約ではない。

| 主張の水準 | 言えること | 避けるべき表現 |
|---|---|---|
| 設計上の推定 | モデル・計算量から性能成立の可能性を説明 | 実測していないのに「性能達成」 |
| テストで確認済み | 指定環境・入力・サンプルで基準に合格 | あらゆる利用環境で「保証」 |
| 形式手法で検証済み | 明示した性質が、仮定・対象範囲内で成立 | 仕様や外部環境全体が「証明済み」 |
| 運用観測済み | 実利用下で得られた統計・事例 | 将来の全負荷に対する「無条件保証」 |

**合格の根拠（Evidence）を、要求の出典（Specification）と切り離して追跡する**ことが、AI生成コードの自己追認を防ぐうえで重要である。

## Security by Design：守るべき境界を先に決める

- 信頼境界、認証・認可、入力検証、秘密情報の扱いを設計時に明示する。
- SAST、依存関係の脆弱性検査、秘密情報検出をリスクに応じてCIへ組み込みます。
- AIエージェントが参照するリポジトリの指示・外部資料は信頼性が一様ではない。権限は最小化し、秘密情報や破壊的操作の扱いを制約する。
- 安全な開発工程は、[NISTのSSDF](https://csrc.nist.gov/pubs/sp/800/218/final)などを参照して整理します。

たとえば「共有フォルダのファイルを別PCに送信する」機能を生成するなら、暗号化ライブラリの選定より前に、**誰が送信できるか、受信側で誰が許可するか、どのディレクトリまで書き込めるか、相手をどう識別するか**を決める必要があります。これらを後から追加すると、通信プロトコルや状態管理そのものを作り直すことがあります。

## Reliability by Design：失敗とキャンセルを通常のシナリオにする

- タイムアウト、リトライの条件、冪等性、キャンセル、バックプレッシャーを設計する。
- 正常系だけでなく、部分失敗・再実行・中断・復旧を受入条件に含める。
- 完全な障害耐性を初期段階で証明できるとは限らないため、統合時の障害注入・運用観測を併用する。

### 例：ファイル転送が途中で中断したら

- 再実行は安全か。二重書き込みや途中ファイルの破損を防げるか。
- 送信側のキャンセルは受信側へ伝わるか。両者が違う結果を認識した場合はどうするか。
- 一時ファイルをどう扱い、いつ最終ファイルとして確定するか。
- ディスク満杯、通信断、権限不足、名前衝突をどう表現するか。

これらは単体テストの数を増やす話ではなく、**状態とプロトコルの設計**です。失敗時の不変条件を明示できれば、AIはその条件を破るテストも作成できます。

## Maintainability by Design：未来の変更を想定する

- DDD的な境界やモジュールの責務を明確にする。
- 依存方向、公開API、状態の所有者、例外・エラーの扱いを一貫させる。
- AIが変更してよいファイル・コンポーネントの範囲を指定し、無関係なリファクタリングを避ける。
- 重要な判断をADRに残し、未来の開発者やAIが設計意図を再利用できるようにする。

**これらは別々のチェック項目ではなく相互制約**です。例えば「速いが認可を省いたAPI」も、「安全だが大量処理で停止するUI」も合格ではない。

## UI/UX・アクセシビリティも生成前の設計対象

UIの受入条件は「画面が表示される」だけでは足りない。**主要タスクの完了経路、読み込み中・空・失敗・キャンセル時の状態、キーボード操作、フォーカス、スクリーンリーダーでの意味、通知の一貫性**などを設計時に決める。視覚差分テストやアクセシビリティ静的検査は有効だが、実際の操作性のValidationや支援技術による確認を置き換えない。

たとえばファイル一覧画面であれば、正常に表示されるケースだけでなく、**読み込み中、結果ゼロ、権限エラー、通信途絶、キャンセル、再試行**の画面状態を先に決めます。キーボード操作やフォーカス移動は、後からCSSや見た目を調整するだけでは埋められない設計上の問題です。

## 依存関係と供給網も設計上の境界

AIが選んだ依存パッケージ、生成したビルドスクリプト、外部コード、CIアクションもレビュー対象である。バージョン固定、由来・ライセンス、脆弱性、権限、再現可能なビルドに必要な情報を、リスクに応じて扱う。Security by Designを単なるSAST実行に縮減しないことが重要です（[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)、[OWASP Developer Guide](https://devguide.owasp.org/)）。

## 品質の衝突をどう扱うか

キャッシュ導入は性能を改善する一方、整合性・メモリ消費・復旧を難しくします。厳密な確認を毎操作に加えれば安全性は高まるかもしれませんが、操作性や遅延を悪化させることもあります。

したがって要求は「性能、セキュリティ、UXを全部最大化」ではなく、以下のように設計します。

| 問い | 例 |
|---|---|
| 絶対に破れない制約は？ | 認可を通らないファイルの取得は不可 |
| どこに余裕を配分する？ | 一覧の初期表示は高速化、全件の整列は段階的に確定 |
| 何を測る？ | p95遅延、ピークメモリ、失敗からの復旧率 |
| 何を試す？ | 権限変更中の操作、通信断、スクリーンリーダー操作 |

## まとめ

品質属性を別々の部署が後から検査するだけでは、構造的な衝突を見落とします。**設計段階で制約を共有し、受入条件と検証方法を紐付け、実測により見直す**ことが、品質をBy Designとして扱う意味です。

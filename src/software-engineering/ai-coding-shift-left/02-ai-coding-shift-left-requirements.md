# AIコーディングの要求設計：DDD・TDD・型・形式手法をどうつなぐか

作成日：2026-10-12 / 更新日：2026-10-12

AIに「この機能を作って」と依頼する前に、何を決めておくべきでしょうか。

設計書を長く書くこと自体が目的ではありません。必要なのは、**利用者の目的、正しい振る舞い、壊してはいけない境界、検証方法**を見える形にすることです。この記事では、DDD・TDD・BDD・Design by Contract・型・形式手法を、互いに競合する流派ではなく「誤りの種類に応じて使い分ける道具」として整理します。


> **注記**
> 本記事のL0〜L3や検証フローは連載独自の運用例です。DDD・TDD・形式手法のいずれかを採用しただけで、要求の妥当性や製品全体の正しさが保証されるわけではありません。


## まず「正しい要求か」と「仕様に合うか」を分ける

両者はともに品質確保に必要ですが、問いが異なります（[NASAによる整理](https://www.nasa.gov/reference/2-4-distinctions-between-product-verification-and-product-validation/)）。

| 概念 | 問うこと | AIコーディングでの典型的な失敗 | 早期の検証手段 |
|---|---|---|---|
| **Validation（妥当性確認）** | その仕様・機能は利用者の真の目的に適切か | 誤った要求を精巧に実装する | ユーザーとの具体例確認、プロトタイプ、業務シナリオ検討 |
| **Verification（検証）** | 成果物は定義した仕様・制約を満たすか | 正しそうな実装とテストが同じ勘違いをする | 契約・型検査・テスト・レビュー・測定 |

**Validationは要求定義だけ、Verificationは実装後だけの活動ではありません。** 試作や運用観測で要求を見直し、設計段階から仕様への適合を点検できます。「仕様には合うが目的には合わない」状態を完了にしないことが大切です。

例：ファイル一覧を全件ソートしてから表示するという仕様を忠実に実装しても、利用者の本来の目的が「大量ファイルからすぐ目的の項目を探すこと」なら、遅い初期表示や段階表示時の並び方も含めて要求自体を見直す必要がある。

## 設計先行は「詳細設計を全部終えること」ではない

生成前に確かめたいのは、例えば認可境界、データ移行方法、主要な性能経路のような、変更費用が高い判断です。UIの細かな余白や小さな内部関数まで先に確定する必要はありません。

要求を次のように段階的に具体化します。

```text
目的・非目標
   ↓
ユースケース（利用者が何を成し遂げたいか）
   ↓
受入条件（正常・異常・境界）
   ↓
制約（既存の責務、性能、安全性、互換性）
   ↓
設計案と検証方法
   ↓
小さな実装 → 実測／テスト → 必要なら仕様を更新
```

### 実装前に記録する項目

AIへの依頼では、変更のリスクに応じて次の項目を揃えます。

| 要素 | 記載事項 | 最小成果物 |
|---|---|---|
| 目的 | 何の問題を解決するか、非目標は何か | 課題票／Issue |
| 仕様 | 正常系、異常系、境界条件 | 受入条件 |
| アーキテクチャ | 既存の責務境界、変更可能な範囲 | 設計メモ、必要ならADR |
| 品質属性 | セキュリティ、性能、信頼性等の優先順位 | 品質チェック項目 |
| 検証 | 必須テスト、計測、レビューの方法 | テスト計画と完了条件 |
| 運用 | ログ、移行、互換性、ロールバック | リリース条件 |

すべての軽微な変更に大きな設計書を要求しない。**後から修正しにくい事項ほど、先に文章化する**。

## DDD・TDD・BDD・契約設計を接続する

| 手法 | シフトレフトへの貢献 | 注意点 |
|---|---|---|
| **DDD** | ドメイン用語、境界づけられたコンテキスト、責務を早期に整理 | 小規模案件への過度な儀式化を避ける |
| **TDD** | 小さな振る舞いとフィードバックを実装に先行させる | テストが実装の内部構造に密結合しないようにする |
| **BDD / Example Mapping** | 利害関係者と具体例・例外を共有する | 形式だけのシナリオ記述にしない |
| **Design by Contract** | 事前条件、事後条件、不変条件を明確化する | 実行時検査と数学的保証を混同しない |
| **ADR** | 大きな設計判断、棄却案、条件を記録する | 小さな実装詳細まですべてADRにしない |

手法を「採用した」と宣言するよりも、**コード生成前に誤った解釈を減らし、検証基準を作れたか**が重要です。

たとえばファイルマネージャーで「ディレクトリAからBへ切り替えた際、遅れて届くAの結果でBの画面を上書きしない」という要求を扱うなら、次のように分業できます。

| 観点 | 生成前に決めること |
|---|---|
| DDD的な責務境界 | 列挙処理と「現在の画面状態」の所有者を分ける |
| BDD / Example Mapping | Aの処理がBより遅れて完了する具体例を列挙する |
| TDD | 結果の完了順を制御する失敗テストを先に作る |
| Design by Contract | 現行の世代ID以外の結果を表示状態へ反映しない不変条件 |
| ADR | 世代ID方式とキャンセルだけで処理する方式を比較・記録する |

**DDDで言葉と責務を揃え、BDDで具体例を出し、TDDでフィードバックを得て、契約で境界を明示する。** 役割を分ければ、全手法を形式的に導入する必要はありません。

## 型・形式手法は何を「早く」保証できるか

静的型、所有権・借用、契約、依存型、モデル検査、定理証明は、対象を正しく定義できれば、ある種の不正な状態を**実行前に排除・検証**できます。これは強力なシフトレフトの一形態です。

| アプローチ | 得意な対象 | 保証の境界 |
|---|---|---|
| 静的型検査 | 型不整合、APIの誤用の一部 | 業務仕様全体は自動では保証されない |
| Rustの所有権・借用検査 | 安全なRustの範囲での特定のメモリ・並行性問題 | 論理バグ、性能、unsafeや外部境界の妥当性は別途検証が必要 |
| プロパティベーステスト | 広範な入力での規則の反例探索 | 有限個のテストだけでは一般に全入力を証明できない |
| Kani等のモデル検査 | 対象範囲での性質検証 | 到達範囲・展開制約・仮定に依存する |
| Verus等の仕様・証明 | 記述した不変条件などの証明支援 | 仕様そのものが正しいか、対象外コードまで保証するかは別問題 |
| Lean等の依存型・定理証明 | 明示した命題の形式的証明 | 実システムとの対応付け、外部I/O、運用要件は別に検討する |

**形式的に証明されたのは「形式化した命題」であって、自然言語の利用者要求すべてではありません。** 前提・実行環境・境界条件を明示し、影響が大きく性質を定義しやすい部分に重点適用するのが現実的です。

### Rustの型で表現できること、できないこと

たとえば状態遷移の種類を列挙型で表現すれば、未定義のケースの一部をコンパイル時に発見できます。

```rust
// 説明用の例。I/OとUIの整合性まで型だけで保証するものではない。
enum LoadState {
    Idle,
    Loading { generation: u64 },
    Ready { generation: u64, entries: Vec<String> },
    Failed { generation: u64, message: String },
}
```

さらに、世代番号とファイル数の取り違えは、別々の型として表現するとコンパイル時に防ぎやすくなります。例えば次のような小さな区別です。

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
struct Generation(u64);

#[derive(Clone, Copy)]
struct EntryCount(usize);

fn is_current(received: Generation, current: Generation) -> bool {
    received == current
}

// is_current(EntryCount(3), Generation(3)); // 型が異なるためコンパイルエラー
```

ただし型が区別されても、**古い完了通知に対して`is_current`を呼び忘れる論理バグ**は防げません。「不正な値を表現しにくくする」型の役割と、「全ての経路で不変条件が保たれる」ことの検証は別です。

しかし「**現在の世代より古い結果を表示しない**」という時系列上の振る舞いは、この型定義だけでは保証されません。テスト、状態遷移の設計、必要に応じた検証を組み合わせます。

VerusやKani、Leanのような方法も、証明対象と仮定を明示した範囲に強みがあります。証明可能性の高い局所的な性質に適用し、外部I/Oや利用者要求の妥当性を別に扱うことが現実的です。

## 生成前に使える最小テンプレート

次の内容をIssueや課題表の**既存の正本レコード**へ追記するところから始められます。

```markdown
## 目的と非目標
- 誰の何を改善するか：
- 今回扱わないこと：

## 妥当性確認（Validation）
- 代表シナリオと確認する人：
- 未確認の仮説：

## 受入条件（Verificationの基準）
- [ ] 正常系：
- [ ] 異常系：
- [ ] 境界条件：

## 設計制約と検証
- 既存の責務・変更範囲：
- 重要な品質属性・リスク：
- 受入条件 → テスト／測定／レビュー：
- 重大判断の承認者：
```

## まとめ

要求のシフトレフトは、先に答えを全部固定することではありません。**生成する前に、誤解すると高くつく問いを共有し、その答えを反証可能にすること**です。

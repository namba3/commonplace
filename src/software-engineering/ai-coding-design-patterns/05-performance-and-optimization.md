# クヌースの「早すぎる最適化」を再考する

作成日：2026-11-02 / 更新日：2026-11-02

*AIコーディング時代のデザインパターン再考 — 第5回*

クヌースの最適化論を原典の意図から捉え直し、AIで変わる探索コストと変わらない検証コストを整理する。

デザインパターンを選ぶ判断と、最適化による複雑さを受け入れる判断には共通点がある。どちらも「作れるか」ではなく、**追加する構造が要求に見合い、正しさを検証し続けられるか**が問われる。

## 「早すぎる最適化」はAI時代にも正しいのか

ドナルド・クヌースの「早すぎる最適化は諸悪の根源」という格言は、しばしば「最初は性能を考えなくてよい」という意味で使われる。しかし、1974年の論文 *Structured Programming with go to Statements* を読むと、少し違った姿が見えてくる[[12]](https://gwern.net/doc/cs/algorithm/1974-knuth.pdf)。

クヌースは、重要でない部分の微小な効率化がデバッグや保守に悪影響を与えることを戒めつつ、**決定的に重要な部分の最適化機会を見逃してはならない**とも述べた。論文中の「97%」「3%」は、測定されたコード行数の割合でも、全プログラムに適用できる統計値でもない。重要でない局所最適化を避けつつ、重要な箇所の改善機会を逃さないための対比表現である。さらに、**重要な箇所を事前の直感で決めつけず、測定によって特定する**必要性を強調している。

興味深いことに、同論文の結論部では、まず理解しやすく正しいプログラムを作り、十分に理解した変換を後から適用して効率化する方法や、その変換を支援するプログラム操作ツールの将来像にも言及している。AIによる最適化候補の探索は、**「理解可能な実装を基準に、変換と検証を繰り返す」**という発想の延長として捉えられる。ただし、AIが提案した書き換えは意味の保存を自動的には保証しない。コンパイラの最適化と同等の信頼性を仮定せず、個別に検証する必要がある。

この主張は、AIコーディングによって無効になるのではない。むしろ、**何を早期に決めるべきか、何を測定まで保留すべきか**を、以前より精密に区別できるようになると考えられる。

### Performance by Designは「早すぎる最適化」と違う

性能要求を設計時から考慮することと、根拠のない局所最適化を施すことは別である。**早期に固定すべきなのは実装の細部ではなく、期待する性能・資源上限・代表的な負荷・測定方法と、後から変更しにくい制約**である。例えばキャッシュ方式を最初から確定するのではなく、必要な応答時間と許容メモリを定義したうえで、実測により導入の要否を決められる。

| 対象 | 設計初期の方針 | 理由 |
| --- | --- | --- |
| 計算量の桁、アルゴリズムの選択 | 早期に検討する | データ量が増えた際の限界を決めるため |
| データモデル、保存形式、I/Oの境界 | 早期に検討する | 後から変更すると広範囲に影響するため |
| 並行処理モデル、メモリ上限 | 早期に制約を明示する | 安全性やスケーラビリティに直結するため |
| キャッシュの導入 | 実ワークロードと整合性要件から判断する | 状態の複雑化や無効化漏れを招くため |
| 特定関数のインライン化、ループ展開、手動SIMD化 | 原則として測定後に判断する | コンパイラ最適化と競合し、可読性を損ねうるため |

例えば、大量の画像を扱うブラウザーで、全ファイルを一度に読み込むか、必要なものだけ段階的に読み込むかは、基本的なアーキテクチャの判断である。大量データへの対応が要求されているなら、初期設計から考慮すべきだ。一方、個々の画素処理ループを手動で最適化するかどうかは、実際にボトルネックと判明してから決めればよい。

また、局所的な改善が全体に効くかどうかも、最適化の優先順位を左右する。例えば、元の処理時間の10%を占める部分だけを2倍速くしても、残る90%が変わらなければ、全体の高速化は`1 / (0.9 + 0.1 / 2) ≒ 1.053`倍にとどまる。実行時間は元の95%となり、**短縮率は5%**だ。高速化倍率と実行時間の短縮率は同じ指標ではない。いわゆる**アムダールの法則**の考え方であり[[13]](https://doi.org/10.1145/1465482.1465560)、画像デコード単体の高速化だけで画面全体の応答性が同じ割合で改善するとは限らない。

**早期に行うべきなのは性能要求と制約の設計であり、避けるべきなのは測定に基づかない局所的な複雑化である。**

### AIが変えるのは最適化の費用対効果

AIは改善候補の実装、別アルゴリズムの試作、ベンチマークの雛形作成などを支援できる。そのため、以前なら作業時間に見合わなかった改善も、比較検討する価値を持つ可能性がある。ただし、最適化の総費用はコードを書く時間だけでは決まらない。

```text
最適化の総期待コスト
  = 実装コスト
  + 正しさ・性能の検証コスト
  + 将来の保守コスト
  + 障害・性能回帰の期待損失
```

ここで「期待損失」は、障害の発生確率と影響を踏まえて見積もるコストを意味する。AIで実装コストが下がっても、残りの項目が同時に下がるとは限らない。想定利用期間の便益と比較するための概念モデルであり、各項目を厳密に金額換算できるとは限らない。例えば、高速化のために複雑な共有キャッシュを導入すれば、並行性、無効化、メモリ消費、障害復旧の検証が必要になる。**生成しやすい改善案と、保守する価値のある改善は異なる**のである。

### 「最適化を作る」から「最適化を探索し、検証する」へ

AI時代に有望なのは、最適化を一回限りの職人的な書き換えではなく、再現可能な探索・検証プロセスとして扱うことだ。

1. **性能要求を定義する**：処理時間、スループット、p95/p99レイテンシ、ピークメモリ、消費電力など、用途に合う指標を選ぶ。
2. **ベースラインを測定する**：代表的な実データと実行環境で測り、測定の揺らぎも記録する。
3. **ボトルネックを特定する**：プロファイラやトレースを用い、印象だけで最適化対象を決めない。
4. **AIで候補を探索する**：アルゴリズム、データ構造、I/O、キャッシュ戦略などの代替案を小さく試す。比較対象を同じ仕様・入力・測定条件にそろえる。
5. **正しさと性能を独立に検証する**：既存テストに加え、境界条件・並行性・メモリ使用量を確認する。マイクロベンチマークだけでなく、実際に近いエンドツーエンドの負荷でも測り、最適化対象と異なるデータでも回帰が起きないか確かめる。
6. **総合評価して採否を決める**：改善幅、測定のばらつき、可読性、保守負荷、回帰リスクを比較する。測定条件・ベースラインの版・採用理由を記録する。

このアプローチを、本稿では **AI-Assisted Empirical Optimization（AI支援の実証的最適化）** と呼ぶ。実装が安くなれば探索する候補は増やせるが、**採用基準まで緩める必要はない**。改善量が測定誤差に埋もれる案や、複雑性だけ増える案を却下できることも成果である。

AIによる最適化能力を過大評価すべきではない。ICML 2026採録版の *SWE-fficiency* は、**NumPyやpandasなど9リポジトリの498件**の性能改善課題で、評価対象の上位エージェントの**Speedup Ratio（SR）が0.23未満**だったと報告している[[14]](https://proceedings.mlr.press/v306/ma26l.html)。これは専門家による改善を基準とした評価であり、他言語・他分野・将来のエージェントへの一般化には注意が必要だ。2025年の先行版とは報告値も異なる。

SRは各課題で「AIのパッチによる高速化倍率 ÷ 専門家のパッチによる高速化倍率」を求め、**課題間では調和平均**で集約する。例えば専門家が5倍速、AIが1.2倍速なら、その課題のSRは`1.2 / 5 = 0.24`である。パッチが未提出・適用不可・指定された正当性テストに不合格の場合は、改善なしとみなして`1 / 専門家の高速化倍率`で採点する。ここでの「正当性」は評価に用いたテストの範囲であり、一般的な意味での機能的正しさの証明ではない。したがって**0.23は「実行時間23%短縮」でも「全課題で専門家の23%の改善」でもない**。

さらに、2026年の別のプレプリントは、最適化ベンチマークの基準パッチを複数環境で再測定した。その結果、SWE-fficiencyでは498課題のうち**411課題**に限り、比較したすべての実行環境で元の妥当性基準を満たしたと報告している[[15]](https://arxiv.org/abs/2607.01211)。これは残る87課題が必ず誤りであるという意味ではない。論文で比較された4種類のクラウド実行環境において、**妥当性判定が環境依存になりうる**という再現性上の注意を示す結果である。また、同研究は公開提出物の順位が集約規則によって変わりうることも報告している。**単一の総合スコアから、特定の最適化手法やエージェントの一般的な優劣を断定しない**ことが重要だ。なお、この研究は査読済み採録論文ではなくプレプリントとして扱う。

したがって、ベンチマークの数値だけを追って、本番ワークロードに無関係なチューニングを量産するのは危険である。計測にはウォームアップやキャッシュ状態、OSの負荷、実行環境の差による揺らぎもある。テスト対象への過適合を避け、複数の負荷条件、測定環境、機能面の不変条件を確認する必要がある。**測定できることと、その測定が実利用の価値を表していることも別問題**だ。

### 三つの原則として整理する

- **Performance by Design**：変更コストの高い性能制約を、設計時から明示する。
- **Optimization by Evidence**：個別の最適化は、測定と正当性検証に基づいて採用する。
- **Automation by AI**：候補探索・実装・比較・回帰検出を自動化し、検証可能な改善の費用を下げる。

この三原則は、クヌースの格言と矛盾しない。AIによって克服されうるのは、主に**最適化の実装や探索にかかる一部のコスト**であり、「重要な部分を見極める必要」や「複雑化の代償」まで消えるわけではない。

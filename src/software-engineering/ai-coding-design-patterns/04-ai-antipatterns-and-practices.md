# AIコーディングのアンチパターンと設計実践

作成日：2026-11-02 / 更新日：2026-11-02

*AIコーディング時代のデザインパターン再考 — 第4回*

過剰抽象化や自己検証の罠を整理し、リスクに比例した設計・検証の実践へ結び付ける。

## AIコーディングで顕在化するアンチパターン

AIによって突然生まれた失敗と、AI以前から存在する失敗を混同しない方がよい。以下の名称は本稿での便宜的な分類であり、標準化されたパターン名ではない。また、二群は厳密には重なり合う。

### 既存の設計上の失敗が増幅される

| 問題 | AIによって目立つ症状 | 対策 |
| --- | --- | --- |
| **Implementation-First Architecture**（実装先行） | 要求や責務境界を定めないまま生成コードを積み重ね、偶然の構造が設計として固定される | 変更範囲、依存方向、重要な不変条件を先に決める |
| **Abstraction Inflation**（過剰抽象化） | 交換予定のない処理にもFactoryやAdapter、設定レイヤーを量産する | 具体的な変更シナリオを説明できない抽象化は作らない |
| **Change Explosion**（変更規模の爆発） | 局所修正に無関係なリファクタリングを混ぜ、レビューしきれない差分を作る | 独立に検証できる小さな変更へ分割する |
| **Speculative Optimization Explosion**（投機的最適化の爆発） | ボトルネックでない箇所を一斉に高速化し、複雑性や性能回帰を招く | 測定値とベースラインを用いて採否を決める（[第5回](05-performance-and-optimization.md)） |

これらはAI生成コード固有の欠陥ではない。**生成の低コスト化は、過剰な変更の実行を容易にする**一方、適切な境界やテストの導入も容易にする。どちらに働くかは、変更の目的と採用基準による。

### エージェント運用で顕在化しやすい失敗

**Self-Validation Trap（自己検証の罠）**：AIが要求を取り違え、その解釈のまま実装とテストを作ると、テストは通っても要求を満たさない。別のAIにテストを作らせるだけでは独立性は保証されない。**独立性は担当するAIの数ではなく、期待結果の根拠と検証経路で決まる**。仕様から先に定義した受け入れ例、既知の正解データ、独立に設計された別実装との比較、性質に基づくテストなどを使い分ける。探索的な開発では、確定した条件から順次テストへ落とし込めばよい。

**Context Fragmentation（文脈の断片化）**：エージェントやセッションの交代で、決定理由、例外条件、既知の制限が失われる。重要な契約と判断の正本を明示し、変更に合わせて更新する。ドキュメントの量を増やすだけでは陳腐化の危険も増すため、型・テスト・コード構造で表現できる情報はそちらを優先する。

**Unbounded Agency（過大な操作権限）**：必要以上のリポジトリ変更権限、機密情報、本番環境アクセスをエージェントに与える。最小権限、実行環境の分離、破壊的操作の承認、操作ログが必要になる。これはGoFのオブジェクト設計ではなく、開発環境の権限境界の問題だ。

共通する誤りは、**生成速度を設計・検証・承認の代替とみなすこと**にある。重要なのはAI生成か人間作成かではなく、変更の影響範囲、不可逆性、誤りの検出困難性だ。

## AI時代に重視したい設計・開発原則

従来のパターンが解決する構造的な問題とは別の層として、次のような**開発・検証のための実践原則**が重要になる。厳密には、GoFのような「オブジェクト指向設計のパターン」と、チーム運用・AIエージェントの制御を含む「開発プロセスの原則」は同じ分類ではない。本稿では両者を混同せず、異なる層として扱う。

| 提案する考え方 | 狙い | 実装・運用の例 |
| --- | --- | --- |
| **Language-Native Design First** | 言語機能で足りるものを過剰にパターン化しない | クロージャ、`enum`、trait、標準イテレーターを優先 |
| **Contract-First Design** | 何が正しい実装かを明示する | 事前条件・事後条件・不変条件・API契約 |
| **Verifiable Architecture** | 設計違反を検出できるようにする | 依存関係テスト、型検査、静的解析、性能テスト |
| **Context-Explicit Architecture** | 設計意図を人とAIが再利用できる | 判断記録、責務定義、正本へのリンク |
| **Failure-Contained Design** | 誤実装・障害の波及を抑制する | モジュール境界、権限制限、タイムアウト、隔離 |
| **Evidence-Driven Development** | 「確認済み」という言葉を証拠と結ぶ | テスト結果、再現手順、差分、ベンチマーク |
| **Optimization by Evidence** | 最適化を推測でなく測定と検証で選別する | プロファイリング、代表ワークロード、性能回帰テスト |

これらは新しい発明を主張する名前ではない。契約、構造テスト、障害隔離、証拠に基づく開発はAI以前から存在する。**AIの導入で、既存の実践を一体として運用する必要性が増した**という整理である。とりわけ、プロンプト中の「守ってほしい」という記述を、可能な範囲で型・テスト・静的検査に落とし込むことが重要だ。ただし、契約やテストの期待値そのものが要求を誤解していれば、機械的な合格は正しさの証明にはならない。

関連する考え方として、AIコーディングエージェントに事前のガイドと事後の検証手段を与える「Harness Engineering」が議論されている[[11]](https://martinfowler.com/articles/harness-engineering.html)。なお、この用語は文脈によってエージェントの実行基盤そのものを指すこともあり、ここでは**開発者がエージェントの作業を導き、検証する仕組み**を意味する。すべての品質を自動チェックだけで保証できるわけではなく、要求の誤解や不必要な機能追加は別の判断を必要とする。

また、検証を厳格にする度合いは一律でなくてよい。表示文言の変更と、暗号処理・並行処理・データ破壊を伴う変更とでは、必要な証拠が異なる。**変更のリスクに比例させて検証を厚くする**方が、過剰な手続きによる開発停滞を防げる。

例えば、次のように検証手段を使い分ける。

| 変更の例 | 最低限の確認 | リスクに応じて加える確認 |
| --- | --- | --- |
| 文言・表示の軽微な修正 | 対象箇所と表示の確認 | アクセシビリティ、複数言語の検証 |
| API契約・永続化形式の変更 | 型・契約テスト、互換性確認 | 移行試験、ロールバック試験 |
| 非同期処理・キャッシュの変更 | 状態遷移と失敗系のテスト | 負荷試験、競合・キャンセル試験 |
| 暗号・認可・機密情報の変更 | 脅威モデル、仕様とテストの照合 | 独立レビュー、負のテスト、権限境界の検査 |

表の検査は例示であり、単一のテストが安全性を証明するという意味ではない。

# 変わらない設計原則とAIコーディング

作成日：2026-11-02 / 更新日：2026-11-02

*AIコーディング時代のデザインパターン再考 — 第2回*

設計原則の持続性と、AIが変える開発上の費用・検証負担を考える。

## 言語が進歩しても残る設計原則

AI時代にも変わらないのは、**計算機とソフトウェアが持つ構造的な制約に由来する問題**である。生成する主体が人間でもAIでも、ネットワーク遅延、I/O待ち、メモリ上限、状態の競合、変更波及は残る。

- **高凝集・低結合**：変更の波及と依存の複雑さを抑える。
- **関心の分離**：異なる変更理由を異なる境界に閉じ込める。
- **明示的な状態と不変条件**：無効な遷移や隠れた副作用を減らす。
- **障害隔離と境界の設計**：一箇所の不具合が全体に拡大することを抑える。
- **適切な抽象化**：変化する部分を分離しながら、不要な間接参照を増やさない。

Rustの所有権・借用、`Option`、`Result`、型状態（Typestate）のような仕組みは、一部の不正状態や誤用をコンパイル時に検出する設計を可能にする。しかし、型検査が成功したからといって、要求仕様・業務ルール・セキュリティ要件がすべて正しいとは言えない。

また、DRYも「コードの文字列を一切重複させないこと」と考えるべきではない。問題は、同じ業務知識や制約が複数箇所で独立に管理され、更新漏れを生むことである。似ているだけの処理を無理に共通化すれば、逆に変更が連鎖する。**偶然似ているコードの重複**と**同じルールの二重管理**は区別したい。

YAGNIも同様に健在だ。AIが将来使うかもしれない拡張機構を短時間で生成できても、その機構を理解・検証・保守する責任は消えない。

## AIコーディングが本当に変えるもの

ここまでの変化は、AI以前から進んでいた。では、AIによって新たに何が変わるのだろうか。

まず、多くの作業で**試作や定型的な実装にかかる労力を減らせる可能性がある**。定型コード、複数実装、テストの雛形、ドキュメントなどを短時間で生成できる場面が増えた。ただし、実際の時間短縮は既存コードへの理解、ツールとの統合、レビュー負荷にも左右される。

次に、**生成の速度と検証の速度が一致しなくなる**。AIが短時間で数十ファイルを変更しても、影響範囲を理解し、仕様との整合性を確認し、障害時の振る舞いを判断するには相応の作業が必要となる。もっとも、AIを検証や分析に使うこともできるため、検証能力が必ず頭打ちになるという意味ではない。

そして、**設計意図が暗黙知のままでは引き継がれにくい**。AIエージェントやセッションが切り替わった際、コードに表れていない判断や例外条件が欠落する可能性がある。

研究結果も一方向ではない。METRの2025年のランダム化比較実験では、対象となった熟練オープンソース開発者にAIツールの使用を**許可した条件**で、禁止した条件より作業時間が平均19%長くなった[[5]](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)。一方、METRは2026年2月の追跡報告でAIによる改善の兆候を示しつつ、参加者選択などの偏りにより改善量を確定できないと説明している[[6]](https://metr.org/blog/2026-02-24-uplift-update/)。これは**AIが常に遅い**という証拠ではない。2025年の研究における対象開発者・タスク・当時のツールという条件と、2026年の追跡研究における選択バイアスは区別する必要がある。さらに同年5月、METRはAI導入後に仕事の構成自体が変わりうることを踏まえ、「導入前からあるタスクの速度向上」「導入後のタスク構成で測る速度向上」「仕事全体の価値向上」を区別する枠組みを示した[[7]](https://metr.org/blog/2026-05-08-task-substitution-and-uplift/)。タスク完了時間、成果物の品質、長期的な保守費用も別々に評価すべき指標である。

2025年のDORA調査も、AIは組織の強みと弱みを増幅すると報告している[[8]](https://dora.dev/research/2025/dora-report/)。したがって、AIの導入だけで設計品質が自然に高まると考えるべきではない。

変化をまとめると、次のようになる。

| 評価軸 | AIで改善が期待できること | それでも残る課題 |
| --- | --- | --- |
| 実装 | 定型処理や複数案の試作を速める | 不要な実装まで増やしやすい |
| 読解・変更 | コード探索や変更案の提示を支援する | 設計意図が暗黙なら誤った変更を選びうる |
| 検証 | テスト生成や静的解析・実行結果の整理を支援する | テストの期待値自体が誤っている可能性がある |
| 運用・保守 | 障害分析や修正候補の提案を支援する | 複雑な状態や依存関係のコストは残る |

設計判断では「実装しやすいか」に加え、**誤りを検出しやすいか、変更を局所化できるか**を問う必要がある。一方、Adapterや境界テストを安価に作れるなら、有益な分離を導入する障壁も下がる。AIは抽象化の必要性を一律に減らすのでも、無制限に正当化するのでもない。

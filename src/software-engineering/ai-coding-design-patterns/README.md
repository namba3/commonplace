# AIコーディング時代のデザインパターン再考

作成日：2026-11-02 / 更新日：2026-11-02

*GoF、現代のプログラミング言語、AIとの相性、そして「早すぎる最適化」を再評価する*

GoFのデザインパターンには、現代言語の機能によって実装が簡素化されたものと、今も構造的な設計問題を解決するものがある。AIはコードの生成・比較を助けるが、変更波及や検証の責任が消えるわけではない。

本連載では、**言語機能・アーキテクチャ・AIを含む開発プロセス**の3層から、パターンの役割とアンチパターンを再評価する。クヌースの「早すぎる最適化」の意味も、Performance by Designと実証的な最適化の観点から考える。

## この連載の結論を先に

デザインパターンの価値は、名前を知っていることや、古典的なクラス構造を再現することでは決まらない。

1. **言語機能で自然に表現できるものは、まず簡潔に書く。** Strategyのために必ずクラス階層を作る必要はない。
2. **変更・状態・依存の境界に必要な構造は残す。** Adapterが扱う契約の接続や、Observerが扱う通知の順序・解除などには、言語機能だけでは消えない設計課題がある。ただし抽象化自体にもコストがある。
3. **AIによる実装の容易さを、採用の根拠にしない。** 変更後の正しさ、追跡可能性、性能、将来の保守費用まで評価する。

第1・2回は背景と基本原則、第3・4回はAIとの相性と実践、第5・6回は性能と実装の具体例を扱う。各回は単独でも読めるようにしている。

## この連載の位置付け

この連載は、特定のGoFパターンを採用するとAIの精度が改善すると実証した研究ではない。具体的なパターンとAIの相性は、変更の局所性、契約の明示性、実行経路の追跡容易性、独立検証の可能性から考察し、その評価方法を提案する。

Rustのコード例は[技術付録](appendix-thumbnail-state.md)に抜粋を掲載する。これは状態遷移を説明するもので、実際のUI統合や画像デコードを実装するものではない。

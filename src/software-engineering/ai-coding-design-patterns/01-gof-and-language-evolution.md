# GoFとプログラミング言語の進化

作成日：2026-11-02 / 更新日：2026-11-02

*AIコーディング時代のデザインパターン再考 — 第1回*

この回では、GoFの歴史的背景と、現代言語によって簡素化された実装形式を分けて整理する。

## はじめに：GoFのパターンは古くなったのか

1994年に刊行された『*Design Patterns: Elements of Reusable Object-Oriented Software*』は、再利用可能なオブジェクト指向設計のための23のパターンを整理し、ソフトウェア開発に共通言語をもたらした[[1]](https://www.oreilly.com/library/view/design-patterns-elements/0201633612/)。Strategy、Adapter、Observerなどの名称は現在も設計上の共通語彙になっている。

ただし、その背景にあるC++やSmalltalkを中心とした設計・実装形式を、現代のRust、Kotlin、Swift、TypeScript、Pythonなどにそのまま持ち込むことが適切とは限らない。高階関数、クロージャ、代数的データ型、パターンマッチング、モジュール機構、ジェネリクスなどを利用すれば、一部の定型的な構造はより簡潔に表現できる。これらの発想の多くは1994年より前から存在していたが、言語ごとに普及度や使い勝手は異なっていた。**「古いから無効」ではなく、「どの言語・要件に対する解法か」を再確認すること**が出発点になる。

一方、言語が進歩したからといって、変更波及、状態の整合性、並行性、障害隔離といった問題そのものが解消するわけではない。ここを混同すると「パターンが不要になった」という結論にも、「古典的な実装構造を守るべきだ」という結論にも誤って傾く。

AIによって設計案を試す負担が下がっても、**作れることと採用する価値があることは異なる**。この連載はパターンの順位表ではなく、採否を判断する方法を考える。後半のAI関連アンチパターン名や実践原則名は、この連載での便宜的な整理である。

## デザインパターンの再評価はAI以前から始まっていた

この議論には重要な先行例がある。Peter Norvigは1996年の講演「Design Patterns in Dynamic Languages」で、GoFの23パターンのうち**16パターンは、少なくとも一部の用途で、LispまたはDylanなら当時のC++より質的に簡単に実装できる**と整理した[[2]](https://norvig.com/design-patterns/design-patterns.pdf)。

ここでの主張は「16パターンが不要になった」「すべて言語機能に吸収された」ということではない。Norvigは、仕組みが言語に溶け込みパターンとして意識されにくくなる場合と、パターンとしての実装が簡素化される場合を区別している。第一級の関数、実行時に値として扱える型、マクロ、マルチメソッド、モジュールなどが存在すると、特定の用途では補助クラスや定型処理が不要、あるいは大幅に簡素化される、という意味だ。**この「16」はLispまたはDylanと当時のC++を比較した結果であって、Rustを含むあらゆる現代言語にそのまま当てはまる数ではない。** 例えばRustの型は、LispやDylanにおける実行時の第一級の型オブジェクトと同じ性質を持つわけではない。言語ごとに利用できる表現力と制約を見直す必要がある。

例えば、Strategyの目的はアルゴリズムを交換可能にすることだが、関数を値として渡せる言語なら、必ずしもStrategyクラスの階層を設ける必要はない。Facadeの目的は複雑なサブシステムに簡潔な入口を設けることだが、言語が充実したモジュール機構を備えていれば、その入口を専用のFacadeクラスで実現するとは限らない。

この分析が示すのは、パターンの**設計上の意図**と、当時の言語に合わせた**実装形式**を分けて評価する必要があるということだ。

## 現代の言語機能はGoFパターンをどう変えたか

「パターンが言語に吸収された」という言い方には注意が必要だ。少なくとも、次の三つを区別したい。

- **仕組みが標準化された**：Iteratorのように、反復の共通インターフェースが言語や標準ライブラリの通常の使い方になった。
- **実装が軽量化された**：StrategyやCommandのように、高階関数やクロージャで専用クラスを減らせる。ただし用途によっては明示的な型が必要になる。
- **問題は引き続き構造的である**：AdapterやFacadeのように、言語機能で書きやすくなっても、異なる契約や公開境界をどう設計するかは残る。

次の表は、代表的なGoFパターンを現代的な実装方法から見直したものである。分類は固定的ではなく、同じパターンでも要件や言語によって位置付けが変わる。

| GoFパターン | 現代的な実現方法 | 現在の位置付け |
| --- | --- | --- |
| Strategy | 関数、クロージャ、trait/interface | 単純なケースでは大幅に簡素化 |
| Command | クロージャ、関数オブジェクト | 実行だけなら簡素化。履歴・取消・永続化には明示的なモデルが必要 |
| Template Method | 高階関数、合成、デフォルト実装 | 継承中心の形式にこだわる必要はない |
| Iterator | 標準イテレーター、generator、stream | 反復の仕組みは標準化。ただし遅延性や所有権などの設計判断は残る |
| Visitor | enum/代数的データ型、パターンマッチング | 対象の型集合が閉じている場合に代替しやすい |
| State | enum、状態遷移表、Typestate | 実行時の状態遷移とコンパイル時の状態制約を使い分ける |
| Factory Method | 生成関数、関連関数、traitを用いた生成契約 | 単純な生成は簡素化。ただしサブクラスに生成処理を委ねる元来の目的とは区別 |
| Builder（GoF本来の意味） | 構築手順と生成表現の分離、高階関数・traitなどによる構築先の切替 | 複数の表現を同じ手順で生成する設計課題は残る。設定用のFluent Builderとは区別 |
| Singleton | モジュール、静的初期化、依存注入 | 実装容易性と、グローバル状態の是非は別問題 |
| Adapter | trait/interfaceと委譲を組み合わせる変換レイヤー | 言語機能は実装を支えるが、異なる契約を接続する役割は残る |
| Facade | モジュールAPI、サービス境界 | 公開APIを整理する設計意図は残る |
| Observer | イベント、リアクティブストリーム、購読API | 実装の定型処理は減るが、順序・再入・解除・障害伝播は残る |
| Bridge | 抽象と実装の分離、依存注入 | 実装交換や複数軸の変化がある場合に重要 |
| Composite | 再帰的データ型、木構造 | 表現は簡潔になっても構造の問題は残る |

### Strategy：クラス階層から高階関数へ

Rustなら、単純なStrategyはクロージャを受け取る関数で表現できる。

```rust
fn apply(value: i32, strategy: impl Fn(i32) -> i32) -> i32 {
    strategy(value)
}

fn main() {
    assert_eq!(apply(10, |x| x * 2), 20);
    assert_eq!(apply(10, |x| x + 5), 15);
}
```

振る舞いを交換するという**設計意図は維持**しながら、専用のStrategy型を毎回作る必要はなくなる。Rustのクロージャには環境をキャプチャする能力もあり、用途に応じて`Fn`・`FnMut`・`FnOnce`の契約を使い分ける[[3]](https://doc.rust-lang.org/stable/book/ch13-01-closures.html)。

ただし、複数の操作を持つ契約、状態やライフサイクルの管理が必要なら、traitと実装型を定義する方が分かりやすい。なお、呼び出す関数を実行時に切り替えるだけなら`Box<dyn Fn(i32) -> i32>`のような選択肢もあり、**動的ディスパッチが必要なだけで直ちに大きなクラス階層が必要になるわけではない**。

### Visitor：enumとパターンマッチングの選択

対象の種類が閉じているなら、Rustの`enum`と`match`で処理を記述できる。

```rust
enum Expr {
    Number(i64),
    Add(Box<Expr>, Box<Expr>),
}

fn evaluate(expr: &Expr) -> i64 {
    match expr {
        Expr::Number(n) => *n,
        Expr::Add(lhs, rhs) => evaluate(lhs) + evaluate(rhs),
    }
}

fn main() {
    let expr = Expr::Add(
        Box::new(Expr::Number(2)),
        Box::new(Expr::Number(3)),
    );
    assert_eq!(evaluate(&expr), 5);
}
```

この形では、`match`で列挙したバリエーションの網羅性をコンパイラが検査できる。単に式を評価したいだけなら、Visitorのための訪問者階層を導入する必要はない。一方、**新しい式の種類を頻繁に増やしたいのか、新しい操作を頻繁に増やしたいのか**によって、適した表現は異なる。これはいわゆる*Expression Problem*（データの種類と操作の双方をどう拡張するか）に関わる問題で、パターンマッチングだけで一般的に解消するものではない。後から未知の実装型を追加できる拡張点にはtraitや動的ディスパッチが向く場合もある。

したがって「Visitorは古いから不要」という結論も単純すぎる。重要なのは、何を変更可能な境界として設計するかだ。

### BuilderとSingleton：同じ名前でも目的を見極める

**Builderには、特に注意したい用語上のずれがある。** GoFのBuilderは、複雑なオブジェクトの**構築過程と表現を分離し、同じ構築手順から異なる表現を作れるようにする**パターンだ。原典では、文書を読み取る手順は共通にしながら、テキストなどの異なる出力表現へ変換する例が示されている[[1]](https://www.oreilly.com/library/view/design-patterns-elements/0201633612/)。現代では、構築先の操作をtraitや関数などで抽象化できる場合があり、GoFに示されたクラス構造をそのまま組む必要はない。しかし、複数の表現をどう作り分けるかという設計問題は残る。

一方、Rustなどでよく「Builder」と呼ぶ**メソッドチェーン型の設定用Builder（Fluent Builder）**は、必須項目の指定や多数のオプションを読みやすく設定するための慣用表現でもある。GoFのBuilderと重なる場合はあるが、両者を同一視できない。単純な設定では、言語によって名前付き引数やデフォルト引数を使え、Rustでも構造体リテラルと`Default`で十分な場合がある。相互依存する設定の検証や段階的構築には専用Builderが有用なこともある。`Default`で値を埋められることと、構築された値が意味的に妥当であることは別である。

Singletonも、静的変数やモジュールを使えば実装自体は容易になる。しかし**あるスコープでインスタンスを一つに制限すること**と、**グローバルな可変状態を共有してよいこと**は別の判断だ。テストの独立性や並行性に問題を持ち込まないかを検討する必要がある。そもそも単一性の単位がプロセス、スレッド、リクエストのどれかによっても設計が変わる。

なお、**Factory Method** も名称に注意が必要だ。GoFでのFactory Methodは、生成するオブジェクトの種類をサブクラスなどの拡張点に委ねる設計を指す。一般に「ファクトリー関数」と呼ばれる生成用関数や、Rustの関連関数（例：`Type::new`）が常にそのまま同じパターンになるわけではない。単純な生成処理なら関数で十分だが、**生成の決定をどの境界に委ねるか**という構造上の判断は残る。

> 言語機能が簡素化するのは、しばしば「実装の儀式」であって、設計上のトレードオフそのものではない。パターン名は**解決策を自動的に選ぶ命令**ではなく、問題と代替案を議論するための語彙として使いたい。

### パターン名ではなく、変更の軸から選ぶ

例えば「動作を差し替えたい」という同じ要望にも、少なくとも三つの実装が考えられる。

| 必要な変化 | まず検討する表現 | 追加の抽象化を検討する条件 |
| --- | --- | --- |
| 呼び出しごとに計算方法だけを変える | 関数・クロージャ | 設定やライフサイクルを伴う場合 |
| 既知の実装候補を実行時に選択する | `enum`と`match`、または関数値 | 候補の追加頻度が高い、または独立した拡張点が必要な場合 |
| コンパイル時に実装型を固定し共通契約で呼び出す | ジェネリクスとtrait境界 | 実行時の切替や異種の実装を一つの集合で扱う必要がある場合 |
| 未知の実装型を実行時に扱う | `dyn Trait`などの動的ディスパッチ | 別ビルドのプラグインなら、ロード方式と安定したABI/APIの設計が別途必要 |

これはRustでの一例であり、言語や配布形態によって選択肢は変わる。`enum`は候補集合を閉じたものとして網羅的に扱う場合に向き、単に処理を差し替えるだけなら関数値の方が簡潔なこともある。**動的ディスパッチと動的ライブラリのロードは別の問題**だ。Rust独自のABIは安定性が保証されないため、独立にビルドされるプラグインの境界には、単にtrait objectを置くだけでなく、例えばC ABIなどを用いた呼び出し規約・データ表現・バージョン管理の設計が必要になる[[4]](https://doc.rust-lang.org/reference/items/external-blocks.html)。重要なのは、**「Strategyを使うべきか」ではなく「何を、いつ、誰が、どの単位で交換するのか」**を先に問うことだ。

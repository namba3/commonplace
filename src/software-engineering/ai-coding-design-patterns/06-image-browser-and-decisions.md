# 画像ブラウザーで考える設計判断

作成日：2026-11-02 / 更新日：2026-11-02

*AIコーディング時代のデザインパターン再考 — 第6回*

画像ブラウザーを例に、言語機能・パターン・検証可能性をどう組み合わせて判断するかを考える。

## ケーススタディ：大量の画像を扱うブラウザーなら

### まず要件と変更の境界を分ける

抽象論だけでは判断しにくいため、10万枚規模の画像フォルダーを閲覧するアプリケーションを例に考えてみよう。要件は「画面上で見えるサムネイルを優先表示し、メモリ使用量を抑え、複数の画像形式に対応する」とする。ここでの**10万枚は設計を考えるための想定規模**であり、実測結果を示すものではない。

| 設計上の関心 | まず検討する選択肢 | 避けたい短絡 |
| --- | --- | --- |
| 表示順の切り替え | 関数やクロージャによる比較・選択 | 並べ替え方式ごとに大きなStrategy階層を作る |
| 対応画像形式の追加 | 共通のデコード契約と形式別Adapter/実装 | UIや一覧処理が各形式の詳細を直接知る |
| 読込状態の表現 | `enum`による`Loading`・`Ready`・`Failed`など | 複数の真偽値の組合せで無効状態を表せてしまう |
| 大量ファイルへの対応 | 遅延読込、上限付きキュー、キャンセル、キャッシュ容量制限 | 全ファイルを最初に一括デコードする |
| AIによる形式追加 | 既存の契約テストと代表画像・破損画像で検証 | 生成したテストだけを根拠に正しさを宣言する |
| 性能の改善判断 | 初回表示時間・スクロール時の遅延・ピークメモリを計測 | 単一デコーダーのマイクロベンチマークだけでUXの改善を判断する |

ここには三つの層が現れる。**言語の機能**で足りる部分は単純に表し、**構造的な境界**が必要な部分は明示的に分離し、**AIによる変更**は契約テストや計測によって検証する。

例えば、読み込み状態を`is_loading`・`has_failed`・`is_ready`という三つの真偽値で持つと、同時に複数が`true`になる矛盾した状態を表現できてしまう。状態の種類が排他的なら、`enum`で表現する方が安全である。特別なStateクラス階層を導入しなくても、**「一度に一つの状態しか取らない」**という制約をデータ構造に埋め込める。ただし、許可された状態遷移まで自動的に保証されるわけではないため、遷移関数とテストで補う。次の例では、その状態表現を非同期処理の結果受理にも利用する。

### 非同期結果をどの表示へ反映してよいか

さらに非同期処理では、「結果が正しい画像である」だけでは不十分だ。フォルダーAを表示中に開始した読み込みが、フォルダーBへ切り替えた後で完了すれば、古い結果が新しい画面へ混入しうる。同じフォルダーでも再読み込みやサムネイルサイズの変更で、以前の結果が無効になる場合がある。

ここでは**UI所有者ID・スロット識別子・世代番号・画像IDを組み合わせた要求ID**を用い、完了結果のIDが現在の読み込み状態と一致するときだけ反映する。**要求IDの照合は、それ以前に無効化処理が実行された場合に限って有効**である。例えばサムネイルサイズや表示フィルターが変わったのに`request`または`clear`を呼ばなければ、旧結果を受理してしまう。変更イベントを必ず無効化につなげるのはUI統合側の契約だ。世代番号だけでは、スロットの破棄・再生成時に値が重複する。そこで、スロットIDは**UI状態の所有者が保持する発行器**から払い出し、同じ発行器の生存期間中は再利用しない。発行をUIスレッドに集約するなら、原子的な共有カウンターは必要ない。さらに、採否判定と状態変更を一つの操作にする。次は表示スロット一つの状態遷移をUIスレッドに集約する例である。**UI状態所有者を丸ごと再生成するとスロットIDが再び1から始まりうる**ため、存続期間が長い発行器から払い出す所有者セッションIDも要求IDに含める。所有者IDを完了通知の別引数にすると配送側が誤って付け替える余地があるが、要求IDに含めれば照合対象を一つにできる。

```text
スロット作成: UI所有の発行器から未使用のスロットIDを払い出す
新しい要求: 世代番号を進め、状態を Loading(所有者ID, スロットID, 世代, 画像ID) にする
完了通知: 現在の Loading(要求ID) と一致するときだけ受理する
成功時: Ready(要求ID, 結果) に遷移する
失敗時: Failed(要求ID, 理由) に遷移する
表示のクリア: 世代番号を進めて Empty に戻す
```

要求IDを照合する状態モデルの考え方とRustコードの抜粋は[技術付録](appendix-thumbnail-state.md)に示す。旧世代の成功・失敗通知、別スロット・別画像の通知、UI所有者を再生成した後の旧通知を拒否できることを、実装時のテストで確認する。ただし、**実際のUI操作が必ず無効化処理を呼び、すべての通知が照合処理を経由することは、状態モデルだけでは保証できない**。そこはUI統合テストで確認する必要がある。

| UI操作・外部変化 | スロット状態に必要な処理 | 別途考慮すること |
| --- | --- | --- |
| フォルダーを切り替える | 旧スロットを破棄するか、旧要求を無効化する | 未完了通知が新しい画面に反映されないこと |
| UI状態の所有者ごと作り直す | 旧通知経路を閉じるか、要求IDに含めた所有者セッションIDを照合する | 新旧の所有者が同じスロットIDを発行しても、旧要求の所有者IDは一致しないこと |
| 同じ画像を再読み込みする | 新しい世代の要求を発行する | 古い成功・失敗通知の拒否 |
| サムネイルの大きさや変換条件を変える | 影響を受けるスロットの要求を更新する | キャッシュキーに変換条件を含める |
| ソート順やフィルターを変える | 表示先が変わるスロットだけを再割当て・無効化する | 再利用可能なデコード結果まで捨てない |
| 元画像の内容が更新される | 必要な表示要求を更新する | ファイルの版・サイズ・更新情報などを組み合わせて鮮度を判定する（更新時刻やサイズだけでは判定できない変更もある） |

ここでは**表示スロットの要求ID**と**デコード結果のキャッシュキー**を区別することが重要だ。前者は「この完了通知を、今の表示先に反映してよいか」を判定し、後者は「異なる表示先でも画像データを再利用してよいか」を判定する。両者を同一視すると、古い結果の混入を防ぐためにキャッシュを過剰に破棄したり、逆に元ファイル・変換条件が変わったのに旧キャッシュを再利用したりする。

**要求IDの照合と表示状態の更新は、一つの操作として扱う**。ワーカーがメッセージを送り、UIスレッドだけが表示状態を更新するなら、[技術付録](appendix-thumbnail-state.md)のようなモデルで実現できる。複数スレッドが直接状態を変更する設計なら、判定と更新を同じロックなどの同期境界に入れる必要がある。

### 状態モデルの保証とUI全体の保証は異なる

責務と検証の境界を混同しないようにしたい。

| 責務 | 状態モデルが対象とする保証 | 別途必要な検証 |
| --- | --- | --- |
| **表示状態の受理判定** | 現在の要求IDに一致する結果だけを一度受理する | 並行更新する構成での同期、ID発行器のライフサイクル |
| **UIイベント・所有者のライフサイクル** | 要求IDに所有者IDを含めて照合する設計を示す | 実際の通知経路が照合処理を必ず通ること、フォルダー・サイズ・フィルター変更時に無効化されること |
| **デコードとキャッシュ** | 状態モデル単体では対象外 | 破損画像、変換条件、ファイル更新、キャッシュの鮮度 |
| **資源とキャンセル** | 状態モデル単体では対象外 | キュー・メモリ上限、キャンセル後に到着する結果の扱い |

とくに**キャンセルは主として無駄な処理の削減、要求IDの照合は表示整合性**を目的とする。キャンセルが間に合わなくても古い結果を拒否できることが必要だ。

対応形式の追加には[第3回](03-patterns-and-ai-affinity.md)のデコーダー契約が関わるが、ソート順の切り替えに同等の抽象化が必要とは限らない。

この例の受け入れ条件には、例えば「表示領域外の大量画像を無制限にデコードしない」「フォルダー切り替え時に不要となった処理をキャンセル対象にでき、キャンセルが間に合わず完了した旧フォルダーの結果も新しい画面へ混入しない」「破損画像によって一覧全体が操作不能にならない」を置ける。これらを検証するには、正常画像だけでなく破損画像・巨大画像・遅いデコード処理・操作の連打などを用意する必要がある。具体的な性能目標値は、対象端末・画像形式・利用者の期待に合わせて定め、実測で確認する。

これは特定の実装を唯一の正解とするものではない。拡張機構を動的にロードするか、対応形式をビルド時に固定するかによっても境界の選び方は変わる。

## 実務で使うための判断手順

従来の「どのGoFパターンを当てはめるか」という問いから、**どうすれば要件を満たし、低コストで検証できるか**という問いに切り替えたい。実装前と変更後に、次の順序で確認する。

1. **問題を定義する。** 本当に困っているのは実装の重複か、変更波及か、性能か、誤用の防止か。
2. **言語の自然な機能を試す。** 関数、`enum`、型、モジュール、標準ライブラリで簡潔に表現できないか。
3. **将来の変更軸を明示する。** 交換すべきものと固定してよいものを区別する。抽象化を選ぶ際は、変更の局所化だけでなく、接続関係と実行経路を追跡できるかも確認する。
4. **契約と検証方法を決める。** 受け入れ条件、境界値、不変条件、依存ルール、必要な性能指標を定める。
5. **小さく実装して証拠を集める。** テスト、ビルド、計測、差分を確認し、見込みと違う案は撤回する。最適化では、採用前の基準値と戻し方も残す。
6. **リスクに比例してレビューする。** 表示変更と、セキュリティ・並行処理・データ永続化の変更を同じ手続きにしない。

判断に迷ったら、**「どの変更要求を満たす抽象化か」「より単純な言語機能ではなぜ不足するか」「何を根拠に正しいと判定するか」**を短く説明する。さらに、AIとの相性を問題にするなら、**変更箇所を探す時間だけでなく、レビュー・再修正・回帰のコスト**も比較する。採用しなかった候補とその理由を残せば、次の設計変更時にも判断を再利用できる。

生成工数の削減が、レビュー・検証・障害対応へ負担を付け替えていないかを考える。**必要な抽象化を、必要な場所に、検証可能な形で置くこと**が目標だ。何もしない、単純化する、抽象化する、計測まで保留する――いずれも根拠があれば妥当な判断になる。

## おわりに：変わるのはパターンの名前ではなく、その選び方

GoFのデザインパターンは、今も設計上の意図を共有するための有用な語彙である。しかし、1990年代の実装構造をそのまま模倣することは、現代的な設計の条件ではない。残る構造的なパターンも、AIとの相性が自動的に良いわけではない。変更の局所性を高める一方で、間接参照を増やすこともある。

言語の進化はAI以前からパターンの実装を簡素化してきた。AIは**試せる選択肢を増やし、その採否と検証の重要性を高める**。

> **優れた設計とは、コードを簡単に生成できる設計ではなく、変更の意図と影響を明確にし、その正しさを継続的に検証できる設計である。**

性能も同様だ。要求は早く設計し、局所最適化の採否は測定で決める。こうした判断を整理するには、少なくとも三つの層を区別したい。

- **Language Idioms**：言語の標準機能と自然な書き方で解決する。
- **Architectural Patterns**：言語を越えて残る依存、責務、状態、障害の境界を設計する。
- **AI Development Practices**：AIを含む変更プロセスの文脈、検証、権限、証拠を整える。

AIが複雑なコードを容易に書けるほど、**複雑さを引き受ける理由を説明し、不要なら作らない判断**に価値が生まれる。パターンの適用数ではなく、要求・代替案・検証結果のつながりを設計の成果として評価したい。

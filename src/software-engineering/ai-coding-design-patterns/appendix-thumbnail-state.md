# 技術付録：非同期サムネイルの状態モデル

作成日：2026-11-02 / 更新日：2026-11-03

*AIコーディング時代のデザインパターン再考 — 第6回の技術付録*

[第6回：画像ブラウザーで考える設計判断](06-image-browser-and-decisions.md)で説明した、古い完了通知を現在の表示スロットへ反映しないための状態モデルを、Rustのコード抜粋とともに示す。

## 実装の対象と設計契約

- **状態**：`Empty`、`Loading`、`Ready`、`Failed`を排他的な`enum`で表す。
- **要求の識別**：`RequestId`にUI所有者セッションID、スロットID、世代番号、画像IDを含める。
- **受理条件**：現在の状態が同じ`RequestId`を持つ`Loading`のときに限り、成功・失敗のどちらかへ一度だけ遷移する。
- **更新の直列化**：表示状態の変更を一つのUIスレッドに集約する前提とし、判定と更新を同じ操作内で行う。
- **識別子の存続期間**：スロットIDは所有者ごとに、所有者セッションIDはその上位の発行器で割り当てる。後者はUI状態を再生成しても存続させる。

次の部分が完了通知の受理判定の中心である。

```rust
fn complete(&mut self, id: RequestId, result: Result<(u32, u32), String>) -> bool {
    if !matches!(&self.state, ThumbnailState::Loading(pending) if *pending == id) {
        return false;
    }
    self.state = match result {
        Ok(size) => ThumbnailState::Ready { request: id, size },
        Err(reason) => ThumbnailState::Failed { request: id, reason },
    };
    true
}
```

これは`ThumbnailSlot`のメソッドの抜粋であり、単独でコンパイルするコードではない。

## 実装時に検証する観点

状態モデルを実装する場合、少なくとも次のケースをテストで確認する。

| 観点 | 主な検証シナリオ |
| --- | --- |
| **新旧の要求** | 新しい要求後の古い成功・失敗、クリア後の遅延結果、同じ画像の再読込 |
| **状態遷移** | 成功・失敗がそれぞれ一度だけ確定し、旧通知によって上書きされない |
| **スロット境界** | 別スロットからの完了通知、破棄・再作成されたスロットへの旧通知 |
| **所有者境界** | UI状態の再生成後に届いた旧所有者の通知、所有者IDが異なる通知 |
| **識別子の整合性** | 画像IDの不一致、同じ所有者内のスロットIDの重複防止 |

ここに挙げた項目は検証時の観点であり、このページにテストコードや実行可能な実装は含めていない。

## 保証しないこと

**要求IDは整合性確認用であり、認証トークンではない。** 任意のIDを偽造できる悪意ある処理を安全に隔離する仕組みではない。また、所有者IDの一意性は同じ発行器の存続期間に限る。発行器そのものを再生成したり、プロセス間で通知を再利用したりする設計には、追加のセッション管理が必要になる。

さらに、サムネイルサイズ、表示条件、元画像などが変わった場合に正しく`request`や`clear`を呼ぶこと、すべての完了通知がUI側の照合を通ること、キャンセル済みタスクが結果を返しても安全であることは、実UIを用いた統合テストで別途確認する必要がある。`RequestId`とキャッシュキーは用途が異なるため、相互の代用品にはならない。

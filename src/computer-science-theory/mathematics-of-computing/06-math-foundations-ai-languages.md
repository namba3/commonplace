# RustからLeanへ：型安全性と形式検証は何が違うのか

作成日：2026-10-12 / 更新日：2026-10-12

> **シリーズ「AI時代に再発見する情報科学の数学的本質」第6章：言語比較**  
> 型付け、メモリ安全性、仕様表現力、証明可能性を分けて見ていきます。

「Rustは安全な言語で、Leanは証明できる言語」。そう聞くと、LeanがRustの上位互換のように見えるかもしれません。

しかし、両者が中心に据えている問題はかなり異なります。

そして、Python、TypeScript、C#、Dafnyなどまで視野を広げると、**安全性や正しさを1つの尺度で順位づけすること自体が不適切**だと分かります。

この章では、AIコーディング時代の言語選択を考えるために、まず保証の種類を分離します。

## 「安全」の意味は少なくとも4つある

| 層 | 何を見るか | それだけでは保証しないこと |
|---|---|---|
| 型の整合性 | 引数、返り値、値の構造 | 要求した業務ルールの正しさ |
| メモリ・実行時安全性 | メモリ管理、参照、境界 | アルゴリズムの正当性 |
| 仕様の表現力 | 事前条件、事後条件、不変条件 | 実装が本当に仕様を満たすか |
| 形式的な検査 | SMT、モデル検査、証明項の検査 | 仕様の妥当性、モデル外の環境 |

型安全なプログラムでも、間違った金額を請求できます。メモリ安全なプログラムでも、誤った順序で決済できます。

逆に、形式的な性質が証明されていても、その性質が十分な仕様でなければ、利用者の期待とは異なる動作をすることがあります。

この区別が、比較の出発点です。

## PythonとTypeScript：柔軟さと静的検査

Pythonは動的型付けの言語ですが、`typing`を使えば型注釈を書けます。型チェッカーによって一部の不整合を実行前に発見できますが、通常のPython実行環境では注釈が自動的にすべて強制されるわけではありません。

TypeScriptはJavaScriptに静的な型検査を導入します。union型、構造的型付け、型推論などは強力です。

ただし、型情報は原則としてJavaScriptへの変換時に消去されます。また、`any`などを通して健全性を犠牲にする経路も存在します。

つまり、どちらも**柔軟性と検査能力のトレードオフ**を持っています。

### C#とJavaの位置づけ

C#やJavaは、静的型付けと管理対象ランタイムによる保護を提供します。

C#ではnullable参照型の解析やパターンマッチングなどが、実装上の制約をより明確に表現する助けになります。

ただし、これらが一般の業務仕様を自動的に数学的証明へ変えてくれるわけではありません。

## Rust：型システムで重要なメモリ安全条件を扱う

Rustの中心的な特徴は、所有権と借用です。

通常のSafe Rustでは、コンパイラが参照の生存期間や別名参照などに関する制約を検査し、重要な種類のメモリ安全性を保証することを目指します。

例えば、ある値への排他的な可変参照を持つ間、その値への競合する参照をどう扱うかが型・借用検査の問題になります。

これは強力ですが、**ソートが正しいこと、請求金額が合っていること、業務ワークフローが正しいこと**をそのまま証明するものではありません。

また、`unsafe`やFFIの境界では別途の健全性条件が必要です。

Rustは、あらゆる意味での正しさを保証する言語ではなく、**システムプログラミングで重要な誤りの一群を、コンパイル時の規則で抑え込む言語**として理解するとよいでしょう。

## Lean：仕様と証明を共通の型理論で扱う

Leanでは、命題を型、証明をその型の項として扱います。さらに依存型によって、値に応じた条件を型で表現できます。

```lean
example (n : Nat) : n + 0 = n := by
  simp
```

この例では、`n + 0 = n`という命題に対する証明を構築し、Leanのカーネルが検査します。

Leanの大きな強みは、**一般的な数学的性質を明示的な仕様と証明として記述できること**です。

一方、仕様を書く負担、証明を成立させる負担、採用した公理や外部コードへの信頼は残ります。「Leanなら、書いたプログラムが自動ですべて正しい」わけではありません。

## Kani・Verus・Dafnyはどこに位置するか

ここからが面白いところです。Leanのような依存型言語を使わなくても、形式検証に取り組む方法はあります。

| 技術 | 中心となる仕組み | 典型的な用途 |
|---|---|---|
| **Kani** | Rust向けモデル検査 | ハーネスに対する性質と経路の検査 |
| **Verus** | Rustに近い記法、仕様、SMT | 事前・事後条件や不変条件の証明 |
| **Dafny** | 言語組み込みの契約とSMT | 仕様付きプログラミングと自動検証 |
| **Lean** | 依存型と証明項、カーネル | 数学的命題やプログラムの性質の証明 |

Kaniで典型的に用いられる有界モデル検査では、ループの展開境界や入力範囲など、検証対象の境界を確認する必要があります。Kaniには実験的なループ契約もありますが、機能ごとの制約を考慮しなければなりません。

VerusやDafnyでは、関数契約や不変条件から検証条件を作り、SMTソルバに証明させます。ただし、未検証コードを信頼する経路や明示的な仮定などは、信頼境界として監査が必要です。

重要なのは、**型、契約、SMT、モデル検査、証明カーネルは、相互排他的な選択肢ではない**という点です。

## Agda・Idris 2・Rocq・Scala 3という別の方向

依存型や型レベルの表現力はLeanだけのものではありません。

- **Agda**：依存型プログラミングと構成的な証明を重視。
- **Idris 2**：依存型を一般のプログラム開発へ生かすことを志向。
- **Rocq（旧Coq）**：対話的定理証明を中心とした成熟した環境。
- **Scala 3**：依存関数型など、実用言語の中で型レベルの表現力を広げる。

同じ「依存型」という言葉が登場しても、**汎用プログラミング、証明支援、既存のエコシステムとの統合**のどれを重視するかは異なります。

単純な順位よりも、目的との適合性を見るべきでしょう。

## AIコーディングで、どれを選ぶべきか

言語選択では、まず「何を作るのか」と「どの性質を保証したいのか」を分けます。以下はあくまで**検討の出発点**であり、既存資産、チームの習熟度、ライブラリ、運用体制によって変わります。

| 目的・制約 | 最初に検討する選択肢 | 保証を強める方法・留意点 |
|---|---|---|
| 既存Webサービスの機能追加 | 利用中のTypeScript、C#、Java、Pythonなど | スキーマ検証、契約テスト、型・静的解析を先に整える |
| OSに近いユーティリティ・低レベル処理 | Rust | Safe Rustを中心に設計。危険な操作の一部をKani／Verusで検証する選択肢もある |
| 境界条件の多い純粋なアルゴリズム | 現用言語＋プロパティテスト、必要ならDafny／Lean | 検証対象を小さな関数に切り出し、不変条件を明示する |
| Rustで書いた重要な計算処理 | Rust＋Kani／Verus | Kaniの探索境界やVerusの信頼した前提を確認する |
| 定理・アルゴリズムの数学的性質が中心 | Lean、Rocq、Agdaなど | 公理、仕様、証明ライブラリ、抽出・実行環境を別々に評価する |
| 大規模な既存Cコードの検証 | Cを維持しつつFrama-Cなど | 全面書き換えの費用と、段階的検証の費用を比較する |

例えば、**Rust製デスクトップアプリをLeanへ全面移植すれば自動的に品質が上がるわけではありません。** 重要なのは、アプリ本体の保守性・安全性と、厳密に証明したい小さな計算部分とを切り分けることです。

反対に、型とテストだけで十分だと最初から決めつけるのも避けたいところです。入力が広く、誤りの影響が大きく、性質を数学的に書きやすい場合には、証明への投資が合理的になる可能性があります。

AIにとって型や仕様が便利なことは確かにあります。生成されたコードが許された構造を満たすか、機械的なフィードバックを返せるからです。

ただし、形式的な表現力が強いほどAIコーディングが必ず容易になるとは限りません。仕様の記述や証明の構築が難しくなる場合もあります。

導入時には次の順序が現実的だと思います。

1. **まず通常の型検査・静的解析・テストを整える。**
2. **重要な境界を契約・不変条件として明示する。**
3. **高い保証が必要な部分にSMT、モデル検査、依存型証明などを選ぶ。**
4. **証明対象外の環境、外部ライブラリ、運用条件を別途確認する。**

例えばデスクトップアプリ全体を形式証明しなくても、ファイルシステムに対する危険な操作や、重要なデータ変換に対象を絞って検証することは考えられます。

## おわりに

RustとLeanは、どちらが「上」かという関係ではありません。

Rustは型と所有権を通じてシステムプログラミングの重要な安全条件を扱い、Leanは仕様と証明を共通の型理論で扱うことを可能にします。

Kani、Verus、Dafnyなどは、その間を埋めたり、別の方法を提供したりします。

**AIコーディング時代の言語選択で重要なのは、何を形式化し、何を機械的に検査し、何を人間が判断するかを設計すること**だと思います。

次章は、AIが生成した証明やコードを受け入れるとき、検証器自身の信頼をどう守るのかを考えます。
